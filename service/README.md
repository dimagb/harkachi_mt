# Сервис прогнозирования пассажиропотока трамвайных маршрутов

Веб-сервис для Единого диспетчерского центра: отдаёт прогноз числа посадок
по маршрутам, остановкам и временным интервалам на трёх горизонтах,
поддерживает корректирующие коэффициенты и выгрузку в CSV и XLSX.

## Запуск

Все данные, нужные сервису, лежат в репозитории, в `data/`. Ничего
скачивать и подкладывать не нужно:

```bash
git clone https://github.com/dimagb/harkachi_mt.git
cd harkachi_mt/service
docker compose up --build
```

Затем открыть:

- http://localhost:8000 — интерфейс: вход, диспетчерская, аналитика
  (сборка `frontend/`, лежит в `static/`, см. ниже)
- http://localhost:8000/api/docs — интерактивная документация API
- http://localhost:8000/api/health — проверка живости

Что лежит в `data/` (около 1.6 МБ):

| Файл | Что это |
|---|---|
| `submission.csv` | прогноз 1.11–31.12.2025, формат сдачи `route;date;hour;prediction` |
| `labels/labels_day_*.csv` | фактические посадки январь–октябрь 2025, для сравнения |
| `spravochniki/*.xlsx` | справочники организаторов: остановки и координаты |

### Интерфейс

`static/` — собранный фронтенд из `frontend/` (React + Vite). Он хранится
в git и копируется в образ, поэтому `docker compose up --build` не требует
ни npm, ни сети. Экраны:

- **вход** — без пароля, достаточно нажать «Войти» (демо: dispatcher /
  dispatcher); роль «Администратор» открывает форму изменений сети;
- **диспетчерская** — карта с линиями маршрутов и списком маршрутов без
  координат, фильтры по маршрутам, дате и часам, коэффициенты с «база /
  сценарий / изменение» через `POST /api/forecast/preview`, лента событий
  сети, рекомендации, разбивка по остановкам с оговоркой, выгрузка XLSX
  с теми же коэффициентами;
- **аналитика** — «День / Месяц / Год» (год склеен из истории и прогноза),
  профиль истории, тепловая карта маршрут × период, рейтинг, точность
  релиза и внешние источники.

Проверен против живого сервиса в контейнере. Пересборка: `cd frontend &&
npm ci && npm test && npm run build`, затем заменить содержимое `static/`
на `frontend/dist/` (`.gitkeep` оставить). Подложка карты — OpenFreeMap,
шрифты — Google Fonts: для них нужен интернет в браузере.

### Запасной интерфейс

`frontend-fallback/index.html` — резерв на случай, если основной
интерфейс не соберётся. Дашборд одним файлом, без сборки и npm:
карта с линиями маршрутов и раскраской по доле, график с вкладками
«День / Месяц / Год» (год склеен из истории и прогноза), фильтры по
маршрутам, периоду и часам, коэффициенты с пересчётом «база / сценарий /
разница», плашка событий сети, разбивка по остановкам с оговоркой,
рекомендации, выгрузка XLSX и CSV, строка состояния. Leaflet и Chart.js —
с CDN, для подложки карты нужен интернет.

```bash
# из корня репозитория: вместо основного интерфейса — резервный
# (сначала убрать из service/static/ всё, кроме .gitkeep)
cp frontend-fallback/index.html service/static/
cd service && docker compose up --build   # интерфейс на http://localhost:8000
```

Без копирования, для отладки: открыть файл с диска с параметром
`index.html?api=http://localhost:8000`.

### Свой прогноз вместо нашего

Положить файл того же формата в `data/submission.csv` и вызвать
`POST /api/reload` — перезапуск не нужен, каталог монтируется в контейнер.

Без Docker:

```bash
cd backend
pip install -r requirements.txt
DATA_DIR=../data RUNTIME_DIR=../runtime uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 2
```

Воркеров два, по числу vCPU. Изменяемое состояние (события сети, агрегаты
приёма, метка перезагрузки) лежит файлами в `RUNTIME_DIR`, и каждый воркер
видит изменения соседа на следующем же запросе — как это устроено,
написано в комментарии к `Dockerfile`. `RUNTIME_DIR` должен быть на
локальной файловой системе; без него состояние пишется в `DATA_DIR`.

Проверка согласованности против запущенного сервиса (меняет его
состояние — запускать до демо):

```bash
python loadtest/consistency.py --url http://localhost:8000
```

## Архитектура

Прогноз считается **пакетно, вне сервиса**, и кладётся файлом. Сервис только
читает готовые значения из памяти и агрегирует их под запрос. Модель в момент
обращения не работает — отсюда десятки миллисекунд p95 под нагрузкой
(см. «Производительность»).

Цепочка модулей:

```
data/                          входные файлы: прогноз, история, справочники
  │
backend/app/pipeline/
  ├── ingest.py                чтение файлов прогноза и истории на старте
  ├── geo.py                   геопривязка: остановки, геометрия маршрутов
  ├── aggregate.py             агрегация: горизонты, маршруты, остановки
  ├── adjust.py                корректирующие коэффициенты
  ├── network_events.py        события сети и вторичный эффект
  ├── validations.py           приём потока валидаций
  ├── shared_state.py          общее состояние воркеров через файлы тома
  └── cache.py                 кеш ответов
  │
backend/app/api/               REST-слой
  ├── health.py                живость, метаданные, перезагрузка данных
  ├── reference.py             справочники маршрутов и остановок
  ├── forecast.py              прогноз с фильтрами
  ├── preview.py               сценарий именованными опциями
  ├── export.py                выгрузка CSV и XLSX
  ├── network.py               события сети
  ├── validations.py           приём валидаций
  └── factors.py               внешние источники и область применимости
  │
static/                        фронтенд (подключается, если есть index.html)
```

Обновление прогноза без перезапуска: заменить `data/submission.csv`
и вызвать `POST /api/reload`.

## Точки входа API

Каждый путь `/api/...` доступен также как `/api/v1/...` — те же обработчики.
`GET /health` — то же, что `/api/health`. В `GET /api/forecast` параметры
`route`, `from`, `to` — алиасы `routes`, `date_from`, `date_to`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | Живость, размер загруженных данных, статистика кеша |
| GET | `/api/meta` | Что загружено: периоды, файлы, предупреждения геопривязки |
| POST | `/api/reload` | Перечитать файлы данных без перезапуска |
| GET | `/api/routes` | Список маршрутов, наличие геометрии, исключения |
| GET | `/api/stops?route=` | Остановки с координатами |
| GET | `/api/geometry?route=` | Геометрия маршрутов в GeoJSON |
| GET | `/api/forecast` | Прогноз с фильтрами и агрегацией |
| GET | `/api/forecast/routes` | Сводка по маршрутам за период |
| GET | `/api/forecast/stops?route=` | Разложение по остановкам (оценочное) |
| GET | `/api/forecast/compare` | Прогноз рядом с фактом сопоставимого периода |
| GET | `/api/export?format=csv\|xlsx` | Выгрузка результатов |
| GET | `/api/export/submission` | Выгрузка в формате сдачи на лидерборд |
| GET | `/api/factors` | Внешние источники данных со ссылками |
| GET | `/api/scope` | Область определения и адаптации модели |
| GET | `/api/network-events` | Активные события сети (`?include_inactive=true` — со снятыми) |
| POST | `/api/network-events` | Добавить событие: закрытие, укорочение, ручной множитель |
| DELETE | `/api/network-events/{id}` | Снять событие |
| POST | `/api/forecast/preview` | Сценарий именованными опциями: погода, событие, сезонная и ручная поправки |
| POST | `/api/admin/reload-forecast` | То же, что `POST /api/reload` |
| POST | `/api/ingest/validations` | Принять батч успешных валидаций |
| GET | `/api/ingest/aggregates` | Накопленные агрегаты: по маршруту и дате или почасово |
| GET | `/api/ingest/status` | Счётчики приёма и последние батчи |

### Параметры `/api/forecast`

| Параметр | Значения | Описание |
|---|---|---|
| `routes` | `17,25` | Маршруты через запятую |
| `date_from`, `date_to` | `2025-12-15` | Период |
| `hour_from`, `hour_to` | `0…23` | Интервал часов |
| `horizon` | `day`, `month`, `year` | Горизонт планирования |
| `granularity` | `hour`, `day`, `month` | Переопределить шаг агрегации |
| `split_by_route` | `true` | Разбить ряд по маршрутам |
| `source` | `forecast`, `history` | Прогноз или факт |

Горизонты: `day` — сутки по часам, `month` — месяц по дням,
`year` — год по месяцам.

### Корректирующие коэффициенты

Применяются к любому запросу прогноза и экспорта, результат виден сразу:

| Параметр | Пример | Описание |
|---|---|---|
| `k_global` | `1.05` | Общий множитель |
| `k_weather` + `weather_from` / `weather_to` | `1.2` | Поправка на погоду в период |
| `k_event` + `event_from` / `event_to` | `1.5` | Поправка на событие |
| `k_routes` | `17:1.1,50:0.8` | Точечные поправки по маршрутам |

Пример ручного сценария (гипотезы диспетчера, не измеренные эффекты):
крупное событие у линии 5–6 декабря (+15%, как опция `MAJOR` каталога
релиза) и ремонт на маршруте 50:

```
GET /api/forecast?horizon=month&k_event=1.15
    &event_from=2025-12-05&event_to=2025-12-06&k_routes=50:0.7
```

Измеренные погодные коэффициенты значимы только для тёплого сезона
(`GET /api/factors`); в ноябре–декабре эффект погоды не значим.

Ответ содержит поле `adjustments` с описанием каждой применённой поправки.

### События сети

Реальное состояние сети, а не what-if: маршрут закрыт на ремонт, укорочен
вечером, для него задана ручная поправка. Хранятся на сервере
(`network_events.json` в `RUNTIME_DIR`; в Docker — том `runtime`) и действуют для всех
пользователей до снятия.

| Тип | Эффект |
|---|---|
| `FULL_CLOSURE` | прогноз = 0 в затронутые дни и часы |
| `SHORTENING` | прогноз × `factor` в затронутые часы |
| `MANUAL_MULTIPLIER` | прогноз × `factor` |

Порядок: сначала поправки пользователя, затем события. Активное закрытие
обнуляет результат при любых коэффициентах; иначе прогноз умножается на
произведение `factor` всех активных событий; в конце `max(прогноз, 0)`.
`valid_to` пустой — событие действует до снятия. Часы пустые — все сутки.

```
POST /api/network-events
{"route": 17, "type": "FULL_CLOSURE", "valid_from": "2025-11-10",
 "valid_to": "2025-11-20", "title": "Ремонт путей", "source_url": "https://..."}
```

Ответы `/api/forecast`, `/api/forecast/routes` и `/api/forecast/stops`
содержат массив `network_events` с событиями на запрошенный период;
значения в `points` уже пересчитаны. Выгрузка `/api/export` — тоже.
`/api/export/submission` и `source=history` событий не учитывают: это
базовый прогноз модели и факт.

Ошибки: `400 INVALID_ROUTE`, `400 INVALID_EVENT`, `409 DUPLICATE_EVENT`,
`404 EVENT_NOT_FOUND`, формат `{"code": ..., "message": ...}`.

**Вторичный эффект — одно измеренное правило.** Закрытие маршрута 17
(`FULL_CLOSURE`) увеличивает прогноз маршрута 11 в 1.1079 раза — только
в дни и часы закрытия и **только в субботу и воскресенье**, после прямых
эффектов событий на самом маршруте 11 и до `max(прогноз, 0)`; если закрыт
и сам 11, там 0. В будни внутри того же закрытия правило не применяется.
В ответе — отдельная запись `secondary_effects` с доказательством
и оговоркой: измерено на 4 выходных днях апреля, поэтому применяется только
к выходным, перенос на будни потребует отдельного измерения; 1.108 —
консервативная нижняя оценка, потому что маршрут 17 тогда возил 1–13%
объёма, а не ноль. Без событий ответы не меняются.

### Ошибки API

Везде один формат: `{"code": "...", "message": "..."}` (плюс `detail`
с тем же текстом для совместимости).

| Код | Когда |
|---|---|
| `400 INVALID_ROUTE` | маршрута нет в наборе задачи (`routes=999`, `route=999`, `k_routes=999:1.1`) |
| `400 INVALID_DATE` | дата не в формате ГГГГ-ММ-ДД |
| `400 INVALID_PERIOD` | `date_from` позже `date_to` |
| `400 OUT_OF_RANGE` | период целиком вне данных; частично вне — 200 и массив `warnings` |
| `400 INVALID_SCENARIO` | коэффициент не число или вне 0.1–5.0, кривой `k_routes` |
| `400 INVALID_PARAMETER` | прочие параметры: `horizon`, `granularity`, часы, `format` |
| `400 INVALID_EVENT`, `409 DUPLICATE_EVENT`, `404 EVENT_NOT_FOUND` | события сети |
| `422 INVALID_BATCH`, `413 BATCH_TOO_LARGE` | приём валидаций |
| `503 FORECAST_NOT_LOADED` | прогноз не загружен |
| `404 NOT_FOUND`, `405 METHOD_NOT_ALLOWED` | нет такого эндпойнта или метода |

### Приём потоковых валидаций

Micro-batch успешных валидаций → почасовые агрегаты «маршрут × дата × час».
Каждая запись уже означает успешную валидацию; если в записи есть поле
`result`, учитывается только `SUCCESS`.

```
POST /api/ingest/validations
{"batch_id": "2025-10-31-001",
 "records": [{"timestamp": "2025-10-31T08:12:10+03:00", "route": 17}]}
```

- **Время** — ISO 8601 обязательно с часовым поясом; группировка по часу
  московского времени (UTC+3).
- **Батч принимается или отклоняется целиком.** Любая ошибка в записи —
  `422 INVALID_BATCH` с номерами записей (не больше пяти ошибок в ответе),
  и такой батч не записывается: исправленный можно прислать с тем же
  `batch_id`.
- **Идемпотентность.** `batch_id` уникален. Повтор отвечает
  `{"status": "ok", "already_processed": true}` и счётчики не удваивает.
  Тот же `batch_id` с другим содержимым тоже не удваивает, но в ответе
  будет `content_matches: false` и предупреждение.
- **Лимиты.** До 50 000 записей в батче (больше — 422 с пояснением);
  тело больше 8 МБ — `413 BATCH_TOO_LARGE` по заголовку, до чтения тела.
- **Хранение.** `validations_state.json` в `RUNTIME_DIR` (в Docker — том `runtime`): агрегаты
  (`route, date, hour, boardings, updated_at`, уникальны по тройке)
  и обработанные `batch_id`. Это состояние сервиса, в git не коммитится.
- **Прогноз не меняется.** Агрегаты нужны пересборке, а не выдаче:
  `/api/forecast` читает релиз прогноза, а не поток.
- В `/api/meta` — `last_ingest_at` и `ingest_batches`.

**Цикл «приём → пересборка» пока не замкнут.** Пересборка
`ml.build_release --runtime` ожидает агрегаты в `runtime.duckdb`, а сервис
пишет их в JSON; конвертера между ними нет. Приём и пересборка по
отдельности работают, вместе — нет.

Проверка руками:

```bash
# 1. отправить батч
curl -s -X POST http://localhost:8000/api/ingest/validations -H "Content-Type: application/json" \
  -d '{"batch_id":"demo-001","records":[{"timestamp":"2025-10-31T08:12:10+03:00","route":17},{"timestamp":"2025-10-31T08:40:00+03:00","route":17}]}'
# 2. агрегаты: у маршрута 17 за 2025-10-31 должно быть 2
curl -s "http://localhost:8000/api/ingest/aggregates?routes=17"
# 3. повторить шаг 1: already_processed: true, в шаге 2 по-прежнему 2
# 4. мета: last_ingest_at заполнен, ingest_batches = 1
curl -s http://localhost:8000/api/meta
```

## Производительность

Замеряется скриптом из `loadtest/` — только стандартная библиотека Python,
ставить ничего не нужно:

```bash
# прогретый кеш: повторяющиеся запросы дашборда
python loadtest/loadtest.py --url http://localhost:8000 --duration 30 --threads 32
# холодный кеш: каждый запрос уникален, кеш ответов не срабатывает ни разу
python loadtest/loadtest.py --url http://localhost:8000 --duration 30 --threads 32 --cold
```

Сценарий смешивает типовые запросы дашборда: здоровье, прогноз на сутки,
прогноз на месяц, сводка по маршрутам, разложение по остановкам, запрос
с корректирующими коэффициентами. Скрипт считает заголовок `X-Cache`
и печатает долю попаданий в кеш — её указывать рядом с RPS.

Проверьте, что лимиты действительно применились, иначе замер окажется
не про 2 vCPU, а про всю машину:

```bash
docker stats tram-forecast --no-stream
```

Либо запускайте без compose, где лимиты задаются явно и наверняка:

```bash
docker build -t tram-forecast .
docker run --rm --name tram-forecast -p 8000:8000 --cpus=2 --memory=2g --memory-swap=2g \
    -v "$PWD/data:/data:ro" -v tram-runtime:/runtime \
    -v "$PWD/../configs:/configs:ro" -e RELEASE_CONFIG=/configs/release.json \
    -v "$PWD/../release:/release:ro" -e FACTOR_OPTIONS=/release/factor_options.json \
    tram-forecast
```

`--memory-swap` равен `--memory`, то есть swap запрещён. Данные — только
чтение; изменяемое состояние — в именованном томе `/runtime`.

Память и CPU во время теста снимать параллельно:

```bash
docker stats tram-forecast
```

### Результаты замера

**Конфигурация.** Контейнер: 2 CPU, 2 GiB, `MemorySwap = 2 GiB` (swap
запрещён), uvicorn, **два воркера** — подтверждено изнутри контейнера.
Прогноз — финальный релиз (маршрут 5 = 0, 14 640 строк). Код — со всеми
последними блоками: правило перетекания 17 → 11, единый формат ошибок,
метаданные релиза в `/api/meta`. Тест — 30 секунд, 32 потока, клиент
`loadtest.py` на той же машине; `docker stats` снимался потоком, раз
в секунду. Перед замером — `docker compose down -v` и чистый том.

Машина: Intel Core i5-13420H, 8 ядер / 12 потоков, 15.7 ГБ RAM, Windows 11
Home, Docker Desktop 4.92.0, Engine 29.8.0, WSL2 (ВМ Docker — 12 CPU,
7.6 ГиБ).

| **RPS** | **2 614** | **497** |
| **latency p50** | 7.5 мс | 61.8 мс |
| **latency p95** | **37.6 мс** | **102.4 мс** |
| latency p99 | 55.6 мс | 130.2 мс |
| latency max | 149.0 мс | 174.1 мс |
| CPU, среднее / пик (из 200%) | 177% / 200% | 190% / 202% |
| RAM, среднее / пик (лимит 2 GiB) | 177 / 184 МиБ | 183 / 195 МиБ |
| Swap | 0 | 0 |

Среднее CPU и RAM — по секундам под нагрузкой (CPU выше 20%), без
прогрева и простоя между прогонами. Swap — `memory.swap.current = 0`
в cgroup контейнера, `memory.swap.max = 0`. В покое до нагрузки: CPU 0.76%,
память 173.8 МиБ; после всех прогонов: CPU 0.58%, 184.5 МиБ (9.01% лимита).

Повторный прогон сразу следом: прогретый 2 576 RPS, p95 39.5 мс; холодный
437 RPS, p95 121.8 мс, ошибок ноль. Это разброс между прогонами на одной
машине: около 1.5% в прогретом режиме и около 12% в холодном.

**Вывод: требование ТЗ — сотни RPS при p95 менее 200–300 мс — выполняется
в обоих режимах.** Даже в холодном, где каждый запрос уникален и кеш
ответов не срабатывает ни разу, p95 102–122 мс. Ошибок ноль, swap ноль,
память стабильна: две копии прогноза в памяти — меньше 200 МиБ, меньше 10%
лимита.

**Про CPU 200% из 200%.** Это полная загрузка, и так и должно быть:
нагрузочный тест ищет потолок пропускной способности — 32 потока шлют
запросы без пауз. Ориентир ТЗ «CPU 60–80% с запасом» относится
к эксплуатационной нагрузке, и запас там огромный: в покое CPU меньше 1%,
а двух с половиной тысяч запросов в секунду дашборду не нужно.

**Замер на другой машине.** Раньше эта таблица была снята Стасом на Intel
Core 5 220H (12 ядер / 16 потоков) на коде до блоков с перетеканием,
ошибками и метаданными: прогретый 3 543 RPS, p95 21.4 мс; холодный 537 RPS,
p95 90.1 мс. Здесь прогретый режим ниже на четверть. Чтобы отделить
машину от кода, тот же коммит, что мерил Стас (`516e4b2`), собран и
прогнан здесь с теми же лимитами и тем же клиентом: 2 085 RPS, p95 43.6 мс
и 434 RPS, p95 127.9 мс, то есть не лучше текущего кода. Разница — машина
(меньше ядер у хоста, на котором заодно работает клиент), а не регресс
в последних правках.

**Сравнение с одним воркером** — замер Стаса на его машине, обе колонки
оттуда. Тот же код, тот же контейнер и тест: индексы прогноза появились
в коммите `8ec2a5f`, а замер на одном воркере снят позже, в `66f7d01`.
Разница — только число воркеров.

| | 1 воркер | 2 воркера |
|---|---|---|
| Прогретый: RPS / p95 | 1 111 / 107.7 мс | 3 543 / 21.4 мс |
| Холодный: RPS / p95 | 166 / 318.2 мс | 537 / 90.1 мс |
| CPU, среднее (из 200%) | 102% | 199–205% |

Тест держит фиксированные 32 потока, поэтому пропускная способность
обратно пропорциональна задержке: RPS ≈ 32 / средняя задержка. На одном
воркере запрос почти всё время стоял в очереди за 31 другим, а второе ядро
простаивало (CPU 102%). Второй воркер разобрал эту очередь: задержка
упала, и RPS вырос в той же пропорции — в 3.2 раза в обоих режимах.
Выигрыш больше двукратного по числу ядер; вероятная причина — один процесс
Python дополнительно терял на конкуренции потоков за GIL. Это
предположение, отдельно не измерялось.

**Согласованность двух воркеров проверена в контейнере:**
`loadtest/consistency.py` — 7 из 7 проверок, ответили оба воркера.
Прогонов два, на двух машинах: у Стаса 40 запросов попали в другой воркер,
чем тот, что принял изменение, на машине из таблицы выше — 58.
Скрипт меняет состояние сервиса (тестовые батчи остаются в томе),
поэтому **перед демо — `docker compose down -v`** и снова
`docker compose up`.

## Ограничения

* **Маршрут 5 — новый**: запущен 16 декабря 2025 (восстановлен спустя
  30 лет, Белорусский вокзал — Метро «Рижская»). Истории по нему нет.
  В сданном релизе прогноз по нему нулевой на весь период — осознанный
  консервативный выбор. Cold start от аналога со дня запуска измерен на
  лидерборде (+0.0046: 0.89447 — лучший результат команды, против 0.88987
  у сданного релиза), но в сданную версию не взят. Сервис отдаёт то, что
  в файле прогноза: скор прогноза, который он показывает, — 0.88987.
* **Остановочная детализация оценочная.** В данных нет привязки валидаций к
  остановкам: `place_id` — это код депо. Целевая величина определена на
  уровне «маршрут × час», разложение по точкам делается по профилю формы
  маршрута. Каждый такой ответ помечен `estimated: true`.
* **Участка как отдельной сущности нет.** ТЗ перечисляет маршрут,
  остановку, участок и интервал; участок покрывается разбивкой по
  остановкам: это последовательность соседних остановок одного направления
  (по `sequence` в `/api/forecast/stops`), и его оценка — сумма `value`
  этих остановок, с той же оговоркой об оценочности.
* **Координаты остановок есть не для всех маршрутов** — только для тех, что
  присутствуют в справочниках. Наличие видно в поле `has_geometry`.
* **Прогнозируются оплаты, а не наполняемость салона.** Телематики в
  датасете нет, безбилетники в целевой величине не отражены.
* **История покрывает 10 месяцев одного года**, поэтому годовой горизонт
  строится качественно, без межгодового сравнения.

Полное описание области определения и адаптации модели: `GET /api/scope`.
