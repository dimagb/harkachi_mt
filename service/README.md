# Сервис прогнозирования пассажиропотока трамвайных маршрутов

Веб-сервис для Единого диспетчерского центра: отдаёт прогноз числа посадок
по маршрутам, остановкам и временным интервалам на трёх горизонтах,
поддерживает корректирующие коэффициенты и выгрузку в CSV и XLSX.

## Запуск

Все данные, нужные сервису, лежат в репозитории, в `data/`. Ничего
скачивать и подкладывать не нужно:

```bash
git clone https://github.com/dimagb/harkachi_mt.git
cd harkachi_mt/service
docker compose up --build
```

Затем открыть:

- http://localhost:8000 — интерфейс
- http://localhost:8000/api/docs — интерактивная документация API
- http://localhost:8000/api/health — проверка живости

Что лежит в `data/` (около 1.6 МБ):

| Файл | Что это |
|---|---|
| `submission.csv` | прогноз 1.11–31.12.2025, формат сдачи `route;date;hour;prediction` |
| `labels/labels_day_*.csv` | фактические посадки январь–октябрь 2025, для сравнения |
| `spravochniki/*.xlsx` | справочники организаторов: остановки и координаты |

### Свой прогноз вместо нашего

Положить файл того же формата в `data/submission.csv` и вызвать
`POST /api/reload` — перезапуск не нужен, каталог монтируется в контейнер.

Без Docker:

```bash
cd backend
pip install -r requirements.txt
DATA_DIR=../data uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

Воркер один намеренно: состояние живёт в памяти процесса, причина
в комментарии к `Dockerfile`.

## Архитектура

Прогноз считается **пакетно, вне сервиса**, и кладётся файлом. Сервис только
читает готовые значения из памяти и агрегирует их под запрос. Модель в момент
обращения не работает — отсюда стабильные единицы миллисекунд под нагрузкой.

Цепочка модулей:

```
data/                          исходные файлы: прогноз, история, справочники
  │
backend/app/pipeline/
  ├── ingest.py                приём и нормализация данных
  ├── geo.py                   геопривязка: остановки, геометрия маршрутов
  ├── aggregate.py             агрегация: горизонты, маршруты, остановки
  ├── adjust.py                корректирующие коэффициенты
  └── cache.py                 кеш ответов
  │
backend/app/api/               REST-слой
  ├── health.py                живость, метаданные, перезагрузка данных
  ├── reference.py             справочники маршрутов и остановок
  ├── forecast.py              прогноз с фильтрами
  ├── export.py                выгрузка CSV и XLSX
  └── factors.py               внешние источники и область применимости
  │
static/                        собранный фронтенд (подключается, если есть)
```

Обновление прогноза без перезапуска: заменить `data/submission.csv`
и вызвать `POST /api/reload`.

## Точки входа API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | Живость, размер загруженных данных, статистика кеша |
| GET | `/api/meta` | Что загружено: периоды, файлы, предупреждения геопривязки |
| POST | `/api/reload` | Перечитать файлы данных без перезапуска |
| GET | `/api/routes` | Список маршрутов, наличие геометрии, исключения |
| GET | `/api/stops?route=` | Остановки с координатами |
| GET | `/api/geometry?route=` | Геометрия маршрутов в GeoJSON |
| GET | `/api/forecast` | Прогноз с фильтрами и агрегацией |
| GET | `/api/forecast/routes` | Сводка по маршрутам за период |
| GET | `/api/forecast/stops?route=` | Разложение по остановкам (оценочное) |
| GET | `/api/forecast/compare` | Прогноз рядом с фактом сопоставимого периода |
| GET | `/api/export?format=csv\|xlsx` | Выгрузка результатов |
| GET | `/api/export/submission` | Выгрузка в формате сдачи на лидерборд |
| GET | `/api/factors` | Внешние источники данных со ссылками |
| GET | `/api/scope` | Область определения и адаптации модели |
| GET | `/api/network-events` | Активные события сети (`?include_inactive=true` — со снятыми) |
| POST | `/api/network-events` | Добавить событие: закрытие, укорочение, ручной множитель |
| DELETE | `/api/network-events/{id}` | Снять событие |

### Параметры `/api/forecast`

| Параметр | Значения | Описание |
|---|---|---|
| `routes` | `17,25` | Маршруты через запятую |
| `date_from`, `date_to` | `2025-12-15` | Период |
| `hour_from`, `hour_to` | `0…23` | Интервал часов |
| `horizon` | `day`, `month`, `year` | Горизонт планирования |
| `granularity` | `hour`, `day`, `month` | Переопределить шаг агрегации |
| `split_by_route` | `true` | Разбить ряд по маршрутам |
| `source` | `forecast`, `history` | Прогноз или факт |

Горизонты: `day` — сутки по часам, `month` — месяц по дням,
`year` — год по месяцам.

### Корректирующие коэффициенты

Применяются к любому запросу прогноза и экспорта, результат виден сразу:

| Параметр | Пример | Описание |
|---|---|---|
| `k_global` | `1.05` | Общий множитель |
| `k_weather` + `weather_from` / `weather_to` | `1.2` | Поправка на погоду в период |
| `k_event` + `event_from` / `event_to` | `1.5` | Поправка на событие |
| `k_routes` | `17:1.1,50:0.8` | Точечные поправки по маршрутам |

Пример: похолодание с 1 по 10 декабря повышает спрос на 15%, на маршруте 50
идут ремонтные работы:

```
GET /api/forecast?horizon=month&k_weather=1.15
    &weather_from=2025-12-01&weather_to=2025-12-10&k_routes=50:0.7
```

Ответ содержит поле `adjustments` с описанием каждой применённой поправки.

### События сети

Реальное состояние сети, а не what-if: маршрут закрыт на ремонт, укорочен
вечером, для него задана ручная поправка. Хранятся на сервере
(`data/network_events.json`, в git не коммитится) и действуют для всех
пользователей до снятия.

| Тип | Эффект |
|---|---|
| `FULL_CLOSURE` | прогноз = 0 в затронутые дни и часы |
| `SHORTENING` | прогноз × `factor` в затронутые часы |
| `MANUAL_MULTIPLIER` | прогноз × `factor` |

Порядок: сначала поправки пользователя, затем события. Активное закрытие
обнуляет результат при любых коэффициентах; иначе прогноз умножается на
произведение `factor` всех активных событий; в конце `max(прогноз, 0)`.
`valid_to` пустой — событие действует до снятия. Часы пустые — все сутки.

```
POST /api/network-events
{"route": 17, "type": "FULL_CLOSURE", "valid_from": "2025-11-10",
 "valid_to": "2025-11-20", "title": "Ремонт путей", "source_url": "https://..."}
```

Ответы `/api/forecast`, `/api/forecast/routes` и `/api/forecast/stops`
содержат массив `network_events` с событиями на запрошенный период;
значения в `points` уже пересчитаны. Выгрузка `/api/export` — тоже.
`/api/export/submission` и `source=history` событий не учитывают: это
базовый прогноз модели и факт.

Ошибки: `400 INVALID_ROUTE`, `400 INVALID_EVENT`, `409 DUPLICATE_EVENT`,
`404 EVENT_NOT_FOUND`, формат `{"code": ..., "message": ...}`.

## Производительность

Замеряется скриптом из `loadtest/` — только стандартная библиотека Python,
ставить ничего не нужно:

```bash
# прогретый кеш: повторяющиеся запросы дашборда
python loadtest/loadtest.py --url http://localhost:8000 --duration 30 --threads 32
# холодный кеш: каждый запрос уникален, кеш ответов не срабатывает ни разу
python loadtest/loadtest.py --url http://localhost:8000 --duration 30 --threads 32 --cold
```

Сценарий смешивает типовые запросы дашборда: здоровье, прогноз на сутки,
прогноз на месяц, сводка по маршрутам, разложение по остановкам, запрос
с корректирующими коэффициентами. Скрипт считает заголовок `X-Cache`
и печатает долю попаданий в кеш — её указывать рядом с RPS.

Проверьте, что лимиты действительно применились, иначе замер окажется
не про 2 vCPU, а про всю машину:

```bash
docker stats tram-forecast --no-stream
```

Либо запускайте без compose, где лимиты задаются явно и наверняка:

```bash
docker build -t tram-forecast .
docker run --rm --name tram-forecast -p 8000:8000 --cpus=2 --memory=2g \
    -v "$PWD/data:/data:ro" -e DATA_DIR=/data tram-forecast
```

Память во время теста снимать параллельно:

```bash
docker stats tram-forecast
```

## Ограничения

* **Маршрут 5 — новый**: запущен 16 декабря 2025 (восстановлен спустя
  30 лет, Белорусский вокзал — Метро «Рижская»). Истории по нему нет.
  В сданном релизе прогноз по нему нулевой на весь период — осознанный
  консервативный выбор. Cold start от аналога со дня запуска измерен на
  лидерборде (+0.0046: 0.89447 — лучший результат команды, против 0.88987
  у сданного релиза), но в сданную версию не взят. Сервис отдаёт то, что
  в файле прогноза: скор прогноза, который он показывает, — 0.88987.
* **Остановочная детализация оценочная.** В данных нет привязки валидаций к
  остановкам: `place_id` — это код депо. Целевая величина определена на
  уровне «маршрут × час», разложение по точкам делается по профилю формы
  маршрута. Каждый такой ответ помечен `estimated: true`.
* **Координаты остановок есть не для всех маршрутов** — только для тех, что
  присутствуют в справочниках. Наличие видно в поле `has_geometry`.
* **Прогнозируются оплаты, а не наполняемость салона.** Телематики в
  датасете нет, безбилетники в целевой величине не отражены.
* **История покрывает 10 месяцев одного года**, поэтому годовой горизонт
  строится качественно, без межгодового сравнения.

Полное описание области определения и адаптации модели: `GET /api/scope`.
