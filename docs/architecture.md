## Принцип

Прогноз считается **пакетно, вне сервиса**, и сохраняется файлом. Веб-сервис
только читает готовые значения из памяти и агрегирует их под запрос. Модель
в момент обращения не работает.

Это даёт мгновенный отклик, снимает риск падения демонстрации на пересчёте
и прямо закрывает нефункциональное требование по производительности.

## Цепочка модулей

```
initial_data/                     сырой датасет хакатона (~10 ГБ, в git нет)
   └─ ml/profile_data.py          разведка сырых данных (ранняя стадия)

service/data/labels/              labels организаторов — закоммичены
data/external/                    внешние источники — закоммичены
   │
   └─ ml/build_release.py         ПАКЕТНЫЙ КОНТУР (requirements-ml.txt),
         │                        --data service/data; сырые данные не нужны
         │  ├── src/data.py        чтение labels, полная сетка
         │  ├── src/pipeline.py    уровень × профиль × календарь,
         │  │                      световой день, режим ремонтов 7/50
         │  ├── data/external/     календарь, погода, события сети
         │  └── проверка полноты, ZERO_ROUTES, калибровка ×1.012
         │
         └─► submission.csv       прогноз: route;date;hour;prediction
             forecast_release.duckdb  тот же прогноз + метаданные
                 │
                 ▼
service/backend/app/              ОНЛАЙН-КОНТУР
   │
   ├─ pipeline/ingest.py          чтение файлов прогноза и истории на старте
   ├─ pipeline/geo.py             геопривязка: остановки, геометрия маршрутов
   ├─ pipeline/aggregate.py       агрегация: горизонты, маршруты, остановки
   ├─ pipeline/adjust.py          корректирующие коэффициенты (what-if)
   ├─ pipeline/network_events.py  события сети: закрытия, укорочения
   ├─ pipeline/validations.py     приём потока валидаций → почасовые агрегаты
   ├─ pipeline/shared_state.py    общее состояние воркеров через файлы тома
   ├─ pipeline/cache.py           кеш ответов
   │
   ├─ api/health.py               живость, метаданные, перезагрузка данных
   ├─ api/reference.py            справочники маршрутов и остановок
   ├─ api/forecast.py             прогноз с фильтрами
   ├─ api/preview.py              сценарий именованными опциями
   ├─ api/export.py               выгрузка CSV и XLSX
   ├─ api/network.py              события сети: GET, POST, DELETE
   ├─ api/validations.py          POST /api/ingest/validations, агрегаты
   └─ api/factors.py              внешние источники, область применимости
         │
         ▼
service/static/                   фронтенд: сборка frontend/ (React + Vite),
                                  хранится в git; резерв — frontend-fallback/
```

Разделение соответствует требованию рубрики: приём и нормализация данных →
признаки и геопривязка → прогноз и агрегация → API → фронтенд.

Обновление статики: `cd frontend && npm run build:service`. Команда собирает
React-приложение и заменяет `service/static/`, сохраняя `.gitkeep`.
Штатный `service/Dockerfile` из main копирует готовые файлы. Исходники
`frontend/` сами по себе при `docker compose up --build` не компилируются.

В интерфейсе карта и сценарии находятся в диспетчерской, три горизонта —
в аналитике. Цвет целого маршрута показывает средний выбранный часовой поток
относительно пикового часа маршрута. Цвет пары соседних остановок — среднее
их оценочных посадок относительно базовых квартилей. Это визуализация,
а не реализованный в UI расчёт суммы для произвольного участка (определение
агрегации участка ниже относится к данным). Отдельной формы выбора границ
участка нет. Ограничения вывода внешних факторов и пояснений API перечислены
в `docs/frontend-tasks.md`.

## Пакетный контур

Запускается вручную, планировщик не нужен:
`python -m ml.build_release --require-clean --data service/data`
(команда и проверка результата — `README.md`, «Быстрый старт»;
подробно — `docs/ml_release.md`).

1. Чтение `labels/labels_day_*.csv` — готовая целевая величина.
2. Построение полной сетки «маршрут × дата × час», пропуски заполняются
   нулями (в файле отсутствуют ночные часы).
3. Модель релиза `statistical-v6`: уровень маршрута по дню недели из
   последних чистых недель, почасовой профиль, производственный календарь,
   поправка на световой день, режим ремонтов маршрутов 7 и 50.
4. Проверка полноты, `ZERO_ROUTES` (маршрут 5 = 0), калибровка ×1.012.
5. Запись `submission.csv` и `forecast_release.duckdb` — одни и те же
   значения. `--require-clean` не даёт собрать релиз из незакоммиченного
   кода.

Проверка качества — rolling backtest и ablation на 4 временных fold
(`scripts/`), только по времени, без случайного разбиения.

Один расчёт — два потребителя: файл для сдачи и таблица для сервиса.
Расхождения между сданным результатом и тем, что показывает дашборд,
исключены по построению.

## Онлайн-контур

Данные грузятся на старте процесса и держатся в памяти: прогноз 14 640
строк, история около 58 тысяч. Повторяющиеся запросы отдаются из кеша.

Обновление прогноза без перезапуска: заменить `data/submission.csv`
и вызвать `POST /api/reload`. Нужно, когда ML-команда подкладывает
новую версию.

### Точки входа API

Каждый путь `/api/...` доступен также как `/api/v1/...`; `GET /health` —
то же, что `/api/health`. Ошибки — единый формат `{code, message}`,
коды в `service/README.md`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | живость, размер данных, статистика кеша |
| GET | `/api/meta` | что загружено, периоды, предупреждения геопривязки |
| POST | `/api/reload` | перечитать файлы без перезапуска (алиас `/api/admin/reload-forecast`) |
| GET | `/api/routes` | маршруты, наличие геометрии, исключения |
| GET | `/api/stops?route=` | остановки с координатами |
| GET | `/api/geometry?route=` | геометрия маршрутов в GeoJSON |
| GET | `/api/forecast` | прогноз с фильтрами и агрегацией |
| POST | `/api/forecast/preview` | сценарий: погода, событие, сезонная и ручная поправки |
| GET | `/api/forecast/routes` | сводка по маршрутам |
| GET | `/api/forecast/stops?route=` | разложение по остановкам (оценочное) |
| GET | `/api/forecast/compare` | прогноз рядом с фактом |
| GET | `/api/export?format=csv\|xlsx` | выгрузка |
| GET | `/api/export/submission` | выгрузка в формате сдачи |
| GET | `/api/factors` | внешние источники со ссылками |
| GET | `/api/scope` | область определения и адаптации модели |
| GET | `/api/network-events` | активные события сети |
| POST | `/api/network-events` | добавить закрытие, укорочение, ручной множитель |
| DELETE | `/api/network-events/{id}` | снять событие |
| POST | `/api/ingest/validations` | батч успешных валидаций |
| GET | `/api/ingest/aggregates` | накопленные агрегаты по маршруту и дате |
| GET | `/api/ingest/status` | счётчики приёма, последние батчи |

Горизонты: `day` — сутки по часам, `month` — месяц по дням, `year` — год
по месяцам.

Корректирующие коэффициенты применяются к любому запросу прогноза и
экспорта: `k_global`, `k_weather` с диапазоном дат, `k_event` с диапазоном,
`k_routes` вида `17:1.1,50:0.8`. Ответ содержит описание применённых
поправок.

События сети — реальное состояние, а не what-if: хранятся на сервере
и действуют для всех. Порядок: база → what-if → события. Активное
закрытие даёт 0 при любых коэффициентах. База (`model_prediction`) не
меняется никогда: ответ каждый раз строится от неё заново. После
добавления или снятия события кеш ответов сбрасывается. Единственный
вторичный эффект — измеренное правило 17 → 11 × 1.1079, только в выходные
внутри закрытия маршрута 17.

## Хранение

Данные помещаются в память процесса, отдельная СУБД не нужна. ТЗ допускает
файловое колоночное хранилище — у нас файловое плюс кеш в процессе.

Входные данные (`data/`) монтируются только на чтение. Изменяемое
состояние — JSON-файлы в `RUNTIME_DIR` (в Docker — именованный том
`runtime`), каждый за своим репозиторием; замена на СУБД трогает только
репозиторий:

- события сети — `network_events.json`, `NetworkEventRepository`;
- приём валидаций — `validations_state.json`: почасовые агрегаты
  (`route, date, hour, boardings, updated_at`, уникальны по тройке)
  и обработанные `batch_id`, `ValidationRepository`;
- метка перезагрузки — `reload.marker`, её меняет `POST /api/reload`.

Файл — источник правды для всех воркеров: процесс перечитывает его, как
только меняется подпись (mtime, размер, inode; один stat на запрос),
а пишет под межпроцессной блокировкой по схеме «прочитать свежее →
изменить → записать атомарно» (`pipeline/shared_state.py`). Подписи файла
событий и метки перезагрузки входят в ключ кеша ответов, поэтому при
изменении все воркеры сразу промахиваются мимо устаревших ответов.

## Приём потока и пересборка: цикл не замкнут

По контракту поток должен кормить пересборку:
батч → проверка → агрегаты → пересборка → новый релиз.

Работает по частям:
- **приём** — `POST /api/ingest/validations`: проверка схемы, маршрута
  и времени, группировка по московскому часу, идемпотентность по
  `batch_id`, агрегаты в `validations_state.json` (`RUNTIME_DIR`);
- **пересборка** — `python -m ml.build_release --runtime runtime.duckdb`
  продлевает историю почасовыми агрегатами.

**Целиком цикл не замкнут:** сервис пишет агрегаты в JSON, а
`ml.build_release --runtime` ожидает таблицу `hourly_aggregates`
в `runtime.duckdb`. Конвертера из JSON в DuckDB нет. Сейчас пересборка
по принятому потоку не запускается, и выдавать этот цикл за рабочий
нельзя. Чтобы замкнуть его, нужен небольшой скрипт: JSON → DuckDB
с теми же колонками, запуск вне сервиса, в ML-окружении, где DuckDB есть.

При росте объёмов схема не меняется: тот же пакетный контур пишет в
Parquet или ClickHouse, API читает оттуда. Внутри одного контейнера
воркеры делят состояние через файлы тома; для реплик на разных машинах
состояние выносится в общее хранилище (файл на локальном томе общим
не будет), а неизменный прогноз читают все реплики одинаково.

## Разделение обучения и обслуживания

Тяжёлые ML-зависимости не входят в serving-образ. Сборка релиза
(`ml/build_release.py`, `src/`) ставит `requirements-ml.txt` — pandas,
numpy, duckdb, pyarrow, pytest — и запускается вне сервиса. Образ сервиса
ставит только `service/backend/requirements.txt`: FastAPI, uvicorn, openpyxl.
Контекст сборки образа — каталог `service/`, поэтому `requirements-ml.txt`
в корне репозитория в образ не попадает даже случайно.

Между контурами — только файл прогноза: сборка пишет его, сервис читает.
Обучение и predict на пользовательском запросе невозможны не по
договорённости, а физически: в образе нет ни кода модели, ни её библиотек.

## Производительность

Один контейнер, uvicorn, **два воркера** — по числу vCPU. Замер на одном
воркере показал упор в пропускную способность одного процесса: CPU 102%
из 200%, холодный p95 318 мс против порога 300. Два воркера стали
возможны после того, как изменяемое состояние переехало из памяти
процесса в файлы тома (см. «Хранение»). Согласованность проверена
на двух воркерах: закрытие, снятие, приём батча и перезагрузка видны
на следующем же запросе в любом воркере, гонки одного батча и одного
события засчитываются ровно один раз (`loadtest/consistency.py`) —
и на хосте, и в контейнере (7 из 7).

Итог в контейнере 2 CPU / 2 GiB, два воркера, 32 потока: прогретый кеш
2 614 RPS при p95 38 мс, холодный 497 RPS при p95 102 мс, ошибок ноль —
**требование ТЗ выполняется в обоих режимах**.

Целевые показатели ТЗ: 2–4 vCPU и 2–4 ГБ RAM, сотни RPS, p95 менее
200–300 мс.

Замер скриптом `loadtest/loadtest.py` — только стандартная библиотека,
два режима: прогретый кеш и холодный (`--cold`). Сценарий смешивает
типовые запросы дашборда. Цифры — в `service/README.md`, раздел
«Производительность»: сняты в контейнере с лимитом 2 CPU / 2 GiB на двух
воркерах, рядом для сравнения — замер на одном.

## Зависимости от внешних данных

| Источник | Для чего | Если недоступен |
|---|---|---|
| Производственный календарь 2025–2026 | праздники и переносы, в прогнозе | CSV в `data/external/`; без него бэктест 0.8868 → 0.8782 |
| Световой день | сдвиг часового профиля, в прогнозе | считается кодом, сеть не нужна |
| Архив погоды (Open-Meteo) | what-if коэффициенты тёплого сезона, в прогноз не входит | CSV в `data/external/` |
| Публикации о ремонтах | режим маршрутов 7 и 50 в прогнозе; события сети с ссылкой | событие задаётся вручную |
| Новость о запуске маршрута 5 | дата запуска (`starts_at`); cold start измерен, в релизе не применён | — |
| Справочники остановок | карта | карта доступна не для всех маршрутов |

Всё внешнее кешируется локально: во время работы сервис не ходит в
интернет, поэтому демонстрация не зависит от доступности сторонних API.
Ссылки и измеренные эффекты — `docs/external-sources.md`.

## Ограничения и перенос модели

Тот же текст отдаёт `GET /api/scope` (поля `limitations` и `adaptation`).

**Ограничения.**

- Маршрут 5 запущен 16.12.2025 и в истории отсутствует. Он есть в сетке прогноза, но в сданном релизе нулевой на весь период. Cold start от маршрута-аналога измерен (+0.0046 на лидерборде), но в сданную версию не взят.
- Остановочная детализация оценочная: привязки валидаций к остановкам в данных нет, place_id — это код депо.
- Участка как отдельной сущности нет. ТЗ перечисляет маршрут, остановку, участок и интервал; участок покрывается разбивкой по остановкам: это последовательность соседних остановок одного направления (по sequence в /api/forecast/stops), и его оценка — сумма value этих остановок, с той же оговоркой об оценочности.
- Координаты остановок есть только для маршрутов 1, 5, 7, 11, 12.
- История покрывает 10 месяцев одного года, поэтому годовая сезонность и межгодовое сравнение недоступны.
- Декабрьский праздничный режим смоделирован по январскому аналогу — это допущение, а не наблюдение.
- Изменения сети (новые участки, закрытия) моделью не предсказываются: закрытия и укорочения задаются вручную событиями сети, прямой эффект применяется поверх прогноза.
- Перетекание спроса при закрытиях: из 23 проверенных пар устойчиво одно правило — закрытие маршрута 17 даёт маршруту 11 × 1.108, измерено на 4 выходных днях апреля. Для остальных пар перетекание в данных не наблюдается. Данные видят только трамвай: ушедших в метро и на автобусы не видно. Правило 17 → 11 применяется в сервисе при активном закрытии маршрута 17 и только в выходные: измерено на выходных, перенос на будни требует отдельного измерения.
- Погода в прогноз не входит: в холодный сезон её эффект не значим; измеренные коэффициенты тёплого сезона доступны как what-if.
- Цикл «приём потока → пересборка» не замкнут. Сервис пишет агрегаты принятых валидаций в JSON, а ml.build_release --runtime ожидает таблицу hourly_aggregates в runtime.duckdb; конвертера из JSON в DuckDB нет. Принятый поток на прогноз пока не влияет.

**Перенос модели.**

- Перенос на новые маршруты: нужна история не менее 8 недель для оценки сезонного профиля. До этого — cold start от маршрута-аналога с даты запуска; на маршруте 5 он измерен, но в релиз не взят.
- Перенос на новый период: релиз пересобирается с новой датой среза (ml.build_release --cutoff), структура модели не меняется; календарь 2026 уже в данных.
- Зависимость от внешних данных мягкая: без них модель работает, но без производственного календаря бэктест падает 0.8868 → 0.8782.

## Запуск

```bash
cd service
docker compose up --build
# http://localhost:8000/api/docs
```

Данные лежат в репозитории, в `service/data/`, и монтируются в контейнер
только на чтение. Изменяемое состояние — в именованном томе `runtime`;
`configs/` и `release/` монтируются для `/api/meta` и preview.
