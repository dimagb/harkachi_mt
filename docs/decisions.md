# Технические решения

Готовые ответы на вопрос «а почему не иначе». Отклонённые варианты
не слабее — они дороже за оставшееся время.

---

## Решения

| Решение | Почему | Что отклонили |
|---|---|---|
| Обучаемся на `labels/`, не на сыром CSV | target уже посчитан, сырьё весит 10 ГБ | разбирать миллионы строк ради готового |
| Медианы, а не средние (для обучаемых моделей — `loss_function='MAE'`) | WAPE ∝ сумма модулей, оптимум — медиана | RMSE и средние: целятся в среднее, завышают на выбросах |
| P50 в сдачу | прямое следствие метрики | среднее или верхний квантиль в зачёт |
| Без лагов | горизонт 61 день, лага в 7 дней для декабря не существует | рекурсивный прогноз с накоплением ошибки |
| Короткое окно профиля | эксперимент: 12 недель дают −0.009 | длинное окно ради объёма выборки |
| Праздничный режим по январю | единственный пример каникул в выборке | ждать, что модель догадается про 31 декабря |
| 31 декабря — частичный праздник (ранняя модель: вес 0.7) | официально нерабочий, но днём ездят; на лидерборде вес 0.5 хуже 0.7 на 0.0020, вес 1.0 не проверялся | 31-е как обычный день |
| Маршрут 5 в сданном релизе — нули на весь период | консервативный выбор ML-команды; релиз 0.88987, тоже выше 0.88. Находка сохранена: маршрут запущен 16.12.2025 (`route_date_start` в справочнике), cold start от аналога дал 0.89447 — лучший результат команды, +0.0046 | cold start в сданной версии: измерен, но не применён |
| Решения по лидерборду | локальная валидация смещена на 0.09 | оптимизация по локальной метрике |
| Python на всём стеке | NFR выполнены и измерены нагрузочным тестом | Java и Spring — в ТЗ это рекомендация, не требование |
| Прогноз считаем батчем | сервис отдаёт готовое, p95 в десятки мс | инференс на каждый запрос |
| Данные в памяти процесса | 73 тысячи строк, отдельная СУБД избыточна | PostgreSQL, ClickHouse |
| Кеш ответов в процессе | в контейнере прогретый кеш 2 614 RPS против 497 холодного — в 5.3 раза; ключ кеша включает подписи файлов состояния, поэтому два воркера не отдают устаревшее | Redis — лишний контейнер |
| Один контейнер, два воркера | НФТ: «сервис — один контейнер»; два воркера по числу vCPU, состояние общее через файлы тома | раздельные контейнеры фронта и бэка |
| Обучение отдельно от обслуживания | в образе сервиса нет ни кода модели, ни pandas: predict на запросе невозможен физически | модель внутри сервиса |
| Разложение по остановкам помечено оценочным | привязки валидаций к остановкам нет | выдавать оценку за измерение |
| Без Kafka и Airflow | пакетный прогон — это скрипт | оркестратор ради красоты схемы |
| Без нейросетей | 66 тысяч строк, 9 маршрутов, два дня | LSTM, TFT, трансформеры |

## Отменено после получения данных

Часть решений принималась до датасета и оказалась неприменима.
Список нужен, чтобы никто не вернул их по инерции.

| Отменено | Причина |
|---|---|
| Прогноз по остановкам как основная единица | метрика по «маршрут × час», `place_id` — это депо |
| Эвристики по времени стоянки | телематики в датасете нет |
| Признак интервала движения, детекция скучивания | нет данных о движении транспорта |
| Детекция безбилетников | строилась на телематике |
| Лаги −1, −7, −14 дней | горизонт 61 день |
| ClickHouse, Kafka, тяжёлый ETL | объём целевой сетки меньше 100 тысяч строк |
| Автоподбор гиперпараметров по валидации | дал −0.018 на лидерборде |

## Что проверено экспериментом

Ранняя модель: семь вариантов, каждый отличался от базового одной вещью.
Полная таблица — в `docs/model.md`.

Итог: ручная подкрутка параметров исчерпана, отклик на уровне третьего
знака. Уровень прогноза почти оптимален, календарные коэффициенты
подобраны верно, короткое окно профиля лучше длинного.

Дальнейший рост дала итоговая модель ML-команды: уровень по режиму
целевой даты, производственный календарь, поправка на световой день —
всё в той же прозрачной декомпозиции. Бустинг (LightGBM) проверен и
в основу не вошёл: устойчивого прироста на временной валидации не дал
(`docs/defense_ml.md`).

## Аргументы для защиты

**«Почему не Java, как рекомендовано в ТЗ?»**
Стек в ТЗ сформулирован как рекомендация, а требование — это NFR по
производительности: один контейнер, сотни RPS, p95 менее 200–300 мс.
Требование выполнено и измерено, цифры в README: в контейнере 2 CPU /
2 GiB — 2 614 RPS при p95 38 мс на прогретом кеше и 497 RPS при p95 102 мс
на холодном. Один язык для модели и сервиса — нет межъязыковой
интеграции; при этом обучение и обслуживание разделены: сервис только
читает готовый прогноз.

**«Где здесь искусственный интеллект?»**
Словами ML-команды (`docs/defense_ml.md`): прогноз — прозрачная
декомпозиция: уровень дня из последних чистых недель того же режима ×
суточный профиль × производственный календарь. На 10 месяцах истории
без прошлого года она устойчиво не уступает бустингу; ML мы используем
там, где он измеримо полезен, — в оценке what-if коэффициентов и
вторичных эффектов сети.

Если спросят про бустинг: LightGBM проверен в роли прямого прогноза,
остаточной поправки и модели профиля — устойчивого прироста на временной
валидации не дал. В 10 месяцах данных нет аналога ноября–декабря, а
бустинг выучивает переходы «весна → лето», которые не переносятся
на осень–зиму. Это результат проверки, а не отсутствие попытки.

**«Почему нет прогноза по остановкам?»**
Данные не позволяют: `place_id` — это код депо, привязки валидаций к
остановкам нет, справочники покрывают не все маршруты. В README
организаторов остановочная детализация помечена как необязательный бонус.
Мы сделали оценочное разложение и явно пометили его как оценку.

**«Как вы проверяли, что модель не выдумывает?»**
Итоговая модель (`docs/defense_ml.md`): 4 временных fold, прогноз только
по данным до даты старта, включая fold с майскими праздниками; rolling
backtest по 8 датам среза и горизонтам 1–60 дней; тесты на отсутствие
утечки после даты среза. Изменение принималось, только если давало
прирост без просадки на отдельных fold. Для ранней модели — журнал
экспериментов на лидерборде, по одной гипотезе за раз.

**«Почему локальная метрика ниже, чем на лидерборде?»**
Это было у ранней модели: локально 0.777, на лидерборде 0.869.
Валидационный период содержит закрытия маршрута 50 по выходным, о которых
модель, обученная на более ранних данных, знать не могла; в финальном
прогнозе эти закрытия уже в обучающем окне. У итоговой модели rolling
backtest — 0.854 в среднем по горизонтам до 60 дней при 0.88987 на
лидерборде.
