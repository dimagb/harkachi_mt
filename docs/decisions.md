# Технические решения

Готовые ответы на вопрос «а почему не иначе». Отклонённые варианты
не слабее — они дороже за оставшееся время.

---

## Решения

| Решение | Почему | Что отклонили |
|---|---|---|
| Обучаемся на `labels/`, не на сыром CSV | target уже посчитан, сырьё весит 10 ГБ | разбирать миллионы строк ради готового |
| `loss_function='MAE'` | WAPE ∝ сумма модулей, оптимум — медиана | RMSE: целится в среднее, завышает на выбросах |
| P50 в сдачу | прямое следствие метрики | среднее или верхний квантиль в зачёт |
| Без лагов | горизонт 61 день, лага в 7 дней для декабря не существует | рекурсивный прогноз с накоплением ошибки |
| Короткое окно профиля | эксперимент: 12 недель дают −0.009 | длинное окно ради объёма выборки |
| Праздничный режим по январю | единственный пример каникул в выборке | ждать, что модель догадается про 31 декабря |
| 31 декабря = 0.7, а не 1.0 | официально нерабочий, но днём ездят; эксперимент подтвердил | формальная логика «нерабочий значит каникулы» |
| Маршрут 5 — cold start от аналога с 16 декабря | маршрут запущен 16.12.2025, `route_date_start` в справочнике; обнуление стоит 0.0046 на лидерборде | нули на весь период «потому что истории нет» |
| Решения по лидерборду | локальная валидация смещена на 0.09 | оптимизация по локальной метрике |
| Python на всём стеке | NFR выполнены и измерены нагрузочным тестом | Java и Spring — в ТЗ это рекомендация, не требование |
| Прогноз считаем батчем | сервис отдаёт готовое, p95 в десятки мс | инференс на каждый запрос |
| Данные в памяти процесса | 73 тысячи строк, отдельная СУБД избыточна | PostgreSQL, ClickHouse |
| Кеш ответов в процессе | 2449 RPS против 336 без него | Redis — лишний контейнер |
| Один контейнер | НФТ сформулировано как «сервис — один контейнер» | раздельные контейнеры фронта и бэка |
| Разложение по остановкам помечено оценочным | привязки валидаций к остановкам нет | выдавать оценку за измерение |
| Без Kafka и Airflow | пакетный прогон — это скрипт | оркестратор ради красоты схемы |
| Без нейросетей | 66 тысяч строк, 9 маршрутов, два дня | LSTM, TFT, трансформеры |

## Отменено после получения данных

Часть решений принималась до датасета и оказалась неприменима.
Список нужен, чтобы никто не вернул их по инерции.

| Отменено | Причина |
|---|---|
| Прогноз по остановкам как основная единица | метрика по «маршрут × час», `place_id` — это депо |
| Эвристики по времени стоянки | телематики в датасете нет |
| Признак интервала движения, детекция скучивания | нет данных о движении транспорта |
| Детекция безбилетников | строилась на телематике |
| Лаги −1, −7, −14 дней | горизонт 61 день |
| ClickHouse, Kafka, тяжёлый ETL | объём целевой сетки меньше 100 тысяч строк |
| Автоподбор гиперпараметров по валидации | дал −0.018 на лидерборде |

## Что проверено экспериментом

Семь вариантов, каждый отличался от базового одной вещью.
Полная таблица — в `docs/model.md`.

Итог: ручная подкрутка параметров исчерпана, отклик на уровне третьего
знака. Уровень прогноза почти оптимален, календарные коэффициенты
подобраны верно, короткое окно профиля лучше длинного.

Дальнейший рост — только через другой инструмент: CatBoost, погода
как признак, разделение уровня и формы.

## Аргументы для защиты

**«Почему не Java, как рекомендовано в ТЗ?»**
Стек в ТЗ сформулирован как рекомендация, а требование — это NFR по
производительности: один контейнер, сотни RPS, p95 менее 200–300 мс.
Требование выполнено и измерено, цифры в README. ML и API в одном
процессе — меньше точек отказа и нет накладных расходов на
межъязыковую интеграцию.

**«Где здесь искусственный интеллект?»**
Решение — ансамбль: статистическая модель даёт устойчивый каркас,
градиентный бустинг ловит нелинейные взаимодействия календаря и погоды.
На валидации показываем сравнение всех трёх вариантов. Честно говорим,
что на рядах такой длины простая модель конкурентна, и это результат
проверки, а не отсутствие попытки.

**«Почему нет прогноза по остановкам?»**
Данные не позволяют: `place_id` — это код депо, привязки валидаций к
остановкам нет, справочники покрывают не все маршруты. В README
организаторов остановочная детализация помечена как необязательный бонус.
Мы сделали оценочное разложение и явно пометили его как оценку.

**«Как вы проверяли, что модель не выдумывает?»**
Валидация повторяет постановку один в один: обучение на январе–августе,
прогноз на сентябрь–октябрь, те же два месяца вперёд без лагов. Плюс
второй фолд. Плюс журнал экспериментов на лидерборде, где каждая гипотеза
проверялась отдельно.

**«Почему локальная метрика ниже, чем на лидерборде?»**
Валидационный период содержит закрытия маршрута 50 по выходным, о которых
модель, обученная на более ранних данных, знать не могла. В финальном
прогнозе эти закрытия уже попадают в обучающее окно. Мы это измерили
и понимаем причину расхождения.
