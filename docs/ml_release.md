# ML release для MVP (по README_MVP_FINAL)

ML отвечает за цепочку `данные → модель → forecast release`. Backend читает готовый
`forecast_release.duckdb`, держит прогноз в RAM и не воспроизводит формулу модели.

> **Состояние сервиса:** текущий бэкенд читает не `.duckdb`, а CSV для жюри
> (`service/data/submission.csv`), который `build_release --submission` пишет из тех же значений.
> Прогноз один и тот же; `release_metadata`, `factor_options` и `network_impact_rules` сервис
> из `.duckdb` пока не читает — коэффициенты и правило продублированы в `GET /api/factors`.
>
> **Цикл «приём → пересборка» не замкнут.** Сервис принимает поток
> (`POST /api/ingest/validations`) и пишет почасовые агрегаты
> `route, date, hour, boardings, updated_at` в `data/validations_state.json`, а `--runtime`
> ожидает таблицу `hourly_aggregates` в `runtime.duckdb`. Конвертера JSON → DuckDB нет:
> приём и пересборка работают по отдельности, вместе — нет.

## Команды
```bash
pip install -r requirements-ml.txt

# финальный релиз: только из закоммиченного кода, чтобы code_git_sha его воспроизводил
python -m ml.build_release --require-clean --output release/forecast_release.duckdb --submission release/submission.csv

# сборка в контейнере: данные в /data
python -m ml.build_release --data /data --output /data/forecast_release.duckdb

# rebuild после ingest: почасовые агрегаты из runtime.duckdb продлевают историю
# ВНИМАНИЕ: сервис пишет агрегаты не в runtime.duckdb, а в data/validations_state.json
# (см. ниже «Состояние сервиса») — конвертера нет, эта команда по принятому потоку не запускается
python -m ml.build_release --data /data --runtime /data/runtime.duckdb --output /data/forecast_release.duckdb

# прогноз следующего периода (история до 31.12.2025 в labels/*.csv)
python -m ml.build_release --data /data --cutoff 2025-12-31 --from 2026-01-01 --to 2026-02-28 --output /data/forecast_release.duckdb

# доказательства: перетекание спроса, ablation внешних источников, rolling backtest
python -m ml.transfer_experiment
python scripts/ablation_external.py
python scripts/rolling_backtest.py
```

`--data` — папка с `labels/labels_day_train.csv`, `labels/labels_day_test.csv` (плюс любые новые месяцы
в `labels/*.csv`) и необязательно `external/` с внешними источниками.
Параметры `--cutoff`, `--from`, `--to` позволяют собрать прогноз на любой период.
Настройки релиза — в `configs/release.json`, параметры модели — в `configs/final_model.json`.

Шаги сборки:
1. Чтение данных (и `hourly_aggregates` из runtime, если передан `--runtime`).
2. Запуск текущей модели (`src/pipeline.py`).
3. Построение прогноза.
4. Применение `ZERO_ROUTES`.
5. Проверка полноты: все маршруты × дни × 24 часа, без дублей и NaN, ≥ 0, нулевые маршруты = 0.
6. Запись во временный файл и замена целевого — сборка с ошибкой не оставляет полузаписанный релиз.
7. Рядом с `.duckdb` — `factor_options.csv` / `factor_options.json` (каталог коэффициентов для `factors.py`
   бэкенда) и, с флагом `--submission`, CSV для жюри с теми же значениями.

## Схема `forecast_release.duckdb`
| Таблица | Содержимое |
|---|---|
| `release_metadata` | `release_id`, `created_at`, `cutoff_date`, `forecast_from`, `forecast_to`, `model_version`, `score`, `code_git_sha`, `schema_version`, `calibration`, `zero_routes`, `default_weather_factor` / `default_event_factor` / `default_season_factor` (= 1.0), `model_prediction_includes`, `not_included`, `n_points`, `details` |
| `forecast_points` | `route`, `date`, `hour`, `model_prediction`; ключ `(route, date, hour)` |
| `factor_options` | `factor_type`, `option_code`, `season`, `value`, `label`, `source` + `is_measured`, `n_days`, `ci_low`, `ci_high`, `significant`, `confirmed`, `condition`, `method` |
| `network_impact_rules` | `event_type`, `source_route`, `target_route`, `factor`, `source` — одно измеренное правило: FULL_CLOSURE 17 → 11 × 1.1079 |
| `forecast_intervals` (необязательная) | `route`, `date`, `hour`, `p10`, `p90` — эмпирический 80%-интервал: квантили «факт / прогноз» из rolling backtest по корзине горизонта и типу часов; охват leave-one-origin-out 0.79 |

**Один релиз — один показываемый прогноз.**
- `score` заполняется, только если md5 прогноза (CSV для жюри) совпадает с `scored_forecast.forecast_md5`
  в `configs/release.json`, то есть это ровно те значения, которые получили скор; иначе `NULL`.
  Поэтому `score` в `/api/meta` всегда относится к тем значениям, которые отдаёт `/api/forecast`.
- `code_git_sha` — коммит, из которого собран релиз. Суффикс `-dirty` означает, что код не был закоммичен
  и по этому SHA релиз не воспроизвести; `--require-clean` в таком случае не даёт собрать релиз.
- Калибровка ×1.012 — часть единственного релиза (`calibration`), подобрана на тестовом периоде.
  Отдельных релизов «для скора» и «для сервиса» нет.

## Что уже внутри `model_prediction`
| Компонент | Внутри | Backend применяет ещё раз |
|---|---|---|
| уровень маршрута по дню недели (последние 4 чистые недели режима целевой даты) | да | нет |
| почасовой профиль | да | нет |
| производственный календарь: праздник → воскресенье, рабочая суббота → пятница | да | нет |
| сезонность модели: режим учебный / летний, новогодние множители | да | нет |
| поправка на световой день (половинная сила) | да | нет |
| известная логика по маршрутам 7 / 50 (режим выходных при ремонте) | да | нет |
| финальная калибровка ×1.012 (часть единственного релиза) | да | нет |
| `ZERO_ROUTES` = 0 | да | нет |
| погода what-if, событие what-if, ручные поправки | нет | да |
| runtime network events | нет | да |

Значения `default_*_factor = 1.0`, поэтому `final_default_prediction == model_prediction`.
Сценарий всегда считается заново от `model_prediction`:
`model_prediction × weather × event × (1 + season_pct/100) × (1 + manual_pct/100)`, затем network overlay.

## `factor_options`: только измеренные коэффициенты
Погода измерена на истории: суточный объём относительно того же маршрута и дня недели ±21 день,
нормированный на сухие дни того же сезона. Эффект зависит от сезона, поэтому опции разделены на
`warm` (апрель–сентябрь) и `cold` (октябрь–март):

| Опция | warm | cold |
|---|---|---|
| NORMAL | 1.000 | 1.000 |
| RAIN_LIGHT | 0.973 (значим, 37 дней) | 0.997 (не значим, 18 дней) |
| RAIN | 0.946 (значим, 23 дня) | не измерено |
| RAIN_HEAVY | 0.897 (значим, 4 дня) | не измерено |
| SNOW | 0.958 (значим, 3 дня) | 0.991 (не значим, 3 дня) |
| HEAT | 0.964 (значим, 12 дней) | — |

Опции без измерений в сезоне отсутствуют. `significant = false` означает, что 90%-интервал включает 1.
`confirmed = true` (измерено и значимо) — только такие коэффициенты можно показывать как подтверждённый
внешний эффект: сейчас это 5 опций тёплого сезона.
EVENT: `NONE = 1.0`; `MEDIUM = 1.05` и `MAJOR = 1.15` — явно ручной сценарий (`source = manual_scenario`,
`confirmed = false`): данных о массовых событиях нет.

Каталог для `factors.py` бэкенда — `factor_options.csv` / `.json` рядом с релизом. Поля:
`factor_code`, `option_code`, `value`, `season` / `scope`, `source`, `method` (как измерено), `confirmed`,
`n_days`, `ci_low`, `ci_high`, `condition`.

Способ измерения погодных коэффициентов (`method`):
- Данные: Open-Meteo ERA5, Москва; осадки, снег и температура за 06–21 ч.
- Ожидаемое значение для чистого дня маршрута (без праздников и аномалий) — медиана того же маршрута и дня недели в пределах ±21 дня.
- Коэффициент = сумма посадок в дни с условием ÷ сумма ожидаемых, нормированная на то же отношение в сухие дни того же сезона.
- 90%-интервал — бутстреп по датам; история — январь–октябрь 2025.

## Перетекание спроса (secondary effects)
`ml/transfer_experiment.py`, результат — `artifacts/transfer_experiment.md`.

| Период | Событие | Дней | Ожидаемое значение |
|---|---|---|---|
| A | маршрут 50 не ходит по выходным с 6.09 (ремонт в Протопоповском переулке) | 16 | будни той же недели × обычное отношение «выходной / будни» (февраль–май) |
| B | изменение участка маршрута 7 Красносельская — Белорусский вокзал, 10.07–10.08 | 32 | медиана того же дня недели 16.06–06.07 и 14–31.08 |
| C | маршрут 17 не работал в выходные 12–13 и 26–27.04 (1–13% обычного объёма) | 4 | будни той же недели × обычное отношение «выходной / будни» (февраль–март) |

Для каждого периода:
- эффект маршрута делится на медианный эффект остальных маршрутов в тот же день — контроль по сети убирает общий сезон, погоду и праздники;
- выходные 5–6.04 исключены из C: в те же дни на маршрутах 1, 11, 12, 50 вышло на 20–40% меньше вагонов (перестройка сети 31.03–06.04).

Коэффициент публикуется, только если выполнены все условия:
- не меньше 4 дней;
- знак одинаков не меньше чем в 80% дней;
- |эффект − 1| > 2 × шум на днях без события;
- placebo-тест (медианы случайных наборов того же размера из дней без события) даёт p < 0.05;
- нет смешивающего фактора.

**Итог: одно измеренное правило.**

| event_type | source_route | target_route | factor | Доказательство |
|---|---|---|---|---|
| FULL_CLOSURE | 17 | 11 | 1.1079 | 4 из 4 дней > 1 (1.028–1.143), шум 4.3%, placebo p < 0.0001, без любого одного дня 1.084–1.131 |

Маршруты 17 и 11 сходятся у Усадьбы Останкино, так что перетекание географически объяснимо.

Не опубликовано:
- **Маршрут 25 при закрытии 17** (+20%, 4 из 4 дней, placebo p < 0.0001): эффект не прошёл заранее заданный порог (шум 10.9%). Порог после результата не меняли.
- **Периоды A и B**: эффекты в пределах шума или знак неустойчив.
- **Рост маршрута 50 на 40% в июле–августе**: это объединение маршрутов 50 и 13 на время ремонта, а не перетекание, поэтому он исключён как смешивающий фактор.

Правило измерено на выходных днях апреля 2025. По контракту бэкенд применяет его при активном
FULL_CLOSURE маршрута 17: `прогноз(11) × 1.1079`. Для остальных пар источник → цель вторичного эффекта нет.

> **Состояние сервиса: правило применяется.** Только при активном `FULL_CLOSURE` маршрута 17,
> только в его дни и часы и **только в субботу и воскресенье**: измерено на выходных, перенос на
> будни потребует отдельного измерения. Коэффициент не меняется: 1.108 — консервативная нижняя
> оценка (маршрут 17 тогда возил 1–13% объёма, а не ноль). После прямых эффектов событий на
> маршруте 11, до `max(прогноз, 0)`.
> Собственное закрытие маршрута 11 сильнее: там 0. В ответах прогноза — отдельная запись
> `secondary_effects` с доказательством и оговоркой; без событий ответы байт в байт прежние.

## Маршрут 5
Решение команды: `ZERO_ROUTES = {5}` — маршрут 5 в релизе = 0. Score релиза — **0.88987** (> 0.88).
Механизм cold start нового маршрута (`effect_type = new_route` в `data/external/network_events.csv`,
`src/models/cold_start.py`) остаётся для будущих запусков маршрутов; для маршрута 5 он перекрыт `ZERO_ROUTES`.

Лучший результат команды на лидерборде — **0.89447**: вариант с cold start маршрута 5 от аналога
с 16.12.2025. Эффект измерен (+0.0046), но в сданный релиз не взят. В зачёт идёт лучший результат
за всё время, поэтому по критерию 1 это ничего не меняет: оба числа выше 0.88.
