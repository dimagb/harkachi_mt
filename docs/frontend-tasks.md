## Три экрана: что где лежит

Договорённость команды — вход, главный экран и аналитика. Важно правильно
разложить содержимое, иначе баллы окажутся на второстепенном экране,
и жюри их не найдёт.

**Главный экран несёт всё, что оценивается.** Карта, три горизонта,
фильтры, панель коэффициентов, разбивка по остановкам, кнопка выгрузки,
блок рекомендаций, строка состояния. Всё это должно быть видно
без перехода куда-либо: жюри должно понять продукт за минуту.

**Экран аналитики — это витрина доказательств.** Туда идёт то, что
интересно, но не оценивается напрямую, плюс два блока, которые как раз
оцениваются, но на главном экране мешают:

- внешние источники с их измеренным эффектом — `GET /api/factors`
  (критерий 2а, по баллу за источник, жюри должно это где-то увидеть);
- область определения модели, ограничения, что нужно для переноса —
  `GET /api/scope` (критерий 2б, два балла);
- прогноз рядом с фактом — `GET /api/forecast/compare`;
- сезонность по месяцам из истории — `horizon=year&source=history`;
- профиль по часам, тепловая карта маршрут × час;
- рейтинг маршрутов с долями — `GET /api/forecast/routes`;
- состояние данных и покрытие — `GET /api/meta`.

Это хороший ход: у жюри появляется место, куда посмотреть на источники
и ограничения, а не искать их в форме.

**Экран входа — читай раздел про авторизацию ниже, там есть риск.**

Не путать два уровня. Верхняя навигация — это экраны: главный
и аналитика. Переключатель «День / Месяц / Год» живёт **внутри** главного
экрана и относится к графику. Если вынести горизонты в верхнюю навигацию
рядом с аналитикой, получится пять непонятных вкладок вместо двух.

## Авторизация: это риск, а не балл

В рубрике за авторизацию не дают **ни одного балла**. Зато она может
отнять почти все остальные: если жюри откроет сервис и увидит форму входа
без подсказки, что вводить, они не увидят ни карты, ни графиков, ни
коэффициентов. В рубрике записано, что при отсутствии запускаемого сервиса
балл существенно снижается — сервис, в который не пускают, для оценки
ничем не отличается от отсутствующего.

Поэтому экран входа делаем **дверью, а не замком**:

- логин и пароль **напечатаны прямо на экране входа**, рядом с полями;
- есть кнопка «Войти как диспетчер», которая не требует ничего вводить;
- те же данные обязательно попадают в README и в поле 3 формы, где
  требуется инструкция для жюри;
- состояние входа живёт на фронте, бекенд его не проверяет — API не
  закрыт токеном. Иначе перестанет работать нагрузочный тест и жюри
  не сможет подёргать эндпойнты руками через `/api/docs`.

Что при этом всё-таки стоит сделать, потому что это усиливает рассказ
о продукте: **разделение ролей**. Диспетчер видит прогноз и сценарии,
администратор дополнительно может добавлять изменения сети (в контракте
`POST /api/network-events` помечен как админский). Переключатель роли
на экране входа даёт ту же историю про продукт для ЕДЦ, но без риска
кого-то не пустить.

Если очень хочется закрыть админское действие — достаточно одного общего
токена в заголовке для `POST` и `DELETE` по событиям сети. Система
пользователей, хеширование паролей и refresh-токены за оставшееся время
не нужны и баллов не принесут.

### Маршрутизация: одна вещь, которую легко проглядеть

В разработке через Vite переход на `/analytics` работает сам. В собранном
виде такого файла на диске нет, поэтому раньше сервис отдавал на него 404 —
то есть при обновлении страницы на вкладке аналитики или при переходе
по прямой ссылке пользователь видел ошибку. **Это уже исправлено
в бекенде:** любой неизвестный путь, не начинающийся с `/api`, отдаёт
`index.html`, а маршрутизацию доигрывает фронт. Проверено на собранной
статике — `/analytics`, `/login` и `/dashboard/route/17` возвращают 200.

Что из этого следует для вас: можно спокойно использовать обычную
маршрутизацию по путям (`react-router` с `BrowserRouter`), хеш в адресе
не нужен. Ассеты сборки складывайте в `assets/` — этот каталог отдаётся
напрямую, минуя подстановку `index.html`.

Неизвестные пути внутри `/api` при этом по-прежнему отдают понятный JSON
с ошибкой, а не страницу — так что опечатка в адресе эндпойнта будет
видна сразу, а не превратится в загадочный HTML в ответе на `fetch`.

## Задачи по приоритету

Если не успеваете всё — делайте строго в этом порядке. Первые три держат
четыре балла, остальное по одному.

### 1. График и три вкладки горизонта

```
GET /api/forecast?routes=17&horizon=day&date_from=2025-12-15&date_to=2025-12-15
GET /api/forecast?routes=17&horizon=month
GET /api/forecast?horizon=year
```

`horizon` принимает `day`, `month`, `year` и сам выбирает шаг сетки: по часам,
по дням, по месяцам. Больше ничего менять не надо.

В ответе массив `points` с полями `key`, `label`, `value` — рисуется напрямую,
без обработки. Рядом `summary` с полями `total`, `peak` (маршрут, дата, час,
значение) и `buckets`.

Параметры фильтрации: `routes` (номера через запятую), `date_from`, `date_to`
(формат ГГГГ-ММ-ДД), `hour_from`, `hour_to` (0–23), `split_by_route=true`
(тогда добавится объект `by_route`), `source=forecast|history`.

**Осторожно с вкладкой «Год».** Прогноз покрывает только ноябрь и декабрь,
поэтому `horizon=year` вернёт две точки. Чтобы показать весь год, нужны два
запроса, история и прогноз, и склейка на фронте:

```
GET /api/forecast?horizon=year&source=history     → январь–октябрь
GET /api/forecast?horizon=year&source=forecast    → ноябрь–декабрь
```

Границу 1 ноября стоит нарисовать вертикальной линией и подписать: слева факт,
справа прогноз. Это хорошо смотрится на защите.

### 2. Карта Москвы

```
GET /api/geometry            → FeatureCollection со всеми маршрутами
GET /api/geometry?route=17   → только один
GET /api/forecast/routes     → сводка с долями и пиками для раскраски
```

Геометрия — настоящие линии по порядку остановок, **отдельно по каждому
направлению**: на маршрут приходит две `Feature` с `LineString`, а не одна.
Толщину или цвет линии брать из `share` или `total` в ответе
`/api/forecast/routes`.

Свойства каждой линии (проверено на реальном ответе):

```json
{
  "type": "Feature",
  "geometry": { "type": "LineString", "coordinates": [[37.61, 55.717], ...] },
  "properties": {
    "route": 7, "direction": 0, "stops": 45,
    "from": "Бульвар Рокоссовского", "to": "Белорусский вокзал"
  }
}
```

Координаты в порядке GeoJSON: **долгота, потом широта**. Многие
картографические библиотеки ждут наоборот — если линии окажутся где-то
в Африке, дело в этом.

**Координаты есть у пяти маршрутов: 1, 5, 7, 11, 12.** Это примерно половина
всего пассажиропотока, так что карта содержательная. Справочник проверен
построчно: у этих маршрутов заполнены все координаты по двум направлениям,
разрывов в нумерации остановок нет.

Остальные пять маршрутов приходят в поле `routes_without_geometry` — их
надо показать списком рядом с картой и подписать, что координат
в справочниках организаторов нет. Честная подпись баллов не отнимает,
а линии, нарисованные наугад, отнимут.

### 3. Фильтры

Маршруты мультивыбором, диапазон дат, диапазон часов. Список маршрутов
с признаками брать из `GET /api/routes`: там есть `in_data`, `has_geometry`,
`stops_count`, `excluded` и текст `note`.

Отдельный случай — **маршрут 5**. Это новый маршрут, запущенный
16 декабря 2025 (восстановлен спустя 30 лет, Белорусский вокзал — Метро
«Рижская»). Истории по нему нет. **В сданном релизе прогноз по маршруту 5 —
нули на весь период, в том числе после 16 декабря.** Ненулевых данных по нему
ждать не надо: это осознанный выбор ML-команды, а не недогруженный файл.

Это не ошибка данных, и скрывать маршрут не надо — наоборот, стоит подписать,
иначе ровный ноль на графике вызовет вопрос «почему пусто». Текст подписи
брать из поля `note` в `GET /api/routes`: бекенд строит его по фактическому
прогнозу, поэтому подпись и график друг другу не противоречат. Дата запуска —
в поле `starts_at`.

### 4. Панель коэффициентов

Это отдельный балл, и формулировка требования — «есть контролы, и прогноз
меняется сразу». Значит контрол двинулся, график перерисовался.

Коэффициенты передаются теми же query-параметрами в тот же эндпойнт:

| Параметр | Что делает | Диапазон |
|---|---|---|
| `k_global` | общий множитель всего прогноза | 0.1–5.0 |
| `k_weather` | поправка на погоду | 0.1–5.0 |
| `weather_from`, `weather_to` | ограничить погоду датами | ГГГГ-ММ-ДД |
| `k_event` | поправка на событие | 0.1–5.0 |
| `event_from`, `event_to` | ограничить событие датами | ГГГГ-ММ-ДД |
| `k_routes` | поправки по маршрутам | `17:1.1,50:0.8` |

Пример:

```
GET /api/forecast?routes=17&horizon=day&date_from=2025-12-15
    &date_to=2025-12-15&k_weather=0.93&k_global=1.05
```

В ответе появится массив `adjustments` с человекочитаемыми подписями
(`label`, например «Погодная поправка ×0.93»). **Его надо выводить на экран** —
это объяснимость, из чего сложился результат.

Чтобы показать «База / Сценарий / Δ%», делайте два запроса: один без
коэффициентов, второй с ними, разницу считайте на фронте. Оба ответа
кешируются в сервисе целиком, так что это дешево.

Ползунки вешать с debounce 150–200 мс, иначе на каждый пиксель полетит запрос.
Ответ приходит из памяти, задержки не будет.

Названия сценариев для выпадающих списков (погода, событие) брать из
`GET /api/factors`. Там сейчас часть полей заполнена заглушкой «ЗАПОЛНИТЬ» —
интерфейс должен это переживать и просто не показывать пустые пункты.
К вечеру заглушки заменятся настоящими значениями, формат не изменится.

### 5. Кнопка выгрузки

```
GET /api/export?format=xlsx&routes=17&date_from=2025-12-01&date_to=2025-12-31
```

Обычная ссылка, браузер скачает сам, никакого JS не нужно:

```jsx
<a href={`/api/export?format=xlsx&${query}`} download>Скачать XLSX</a>
```

Принимает те же фильтры и те же коэффициенты, что и прогноз, — то есть
выгружается именно то, что человек видит на экране. `format` принимает
`csv` или `xlsx`.

### 6. Разбивка по остановкам

```
GET /api/forecast/stops?route=17&date_from=2025-12-01&date_to=2025-12-31
```

Открывается панелью по клику на маршрут. Точная схема элемента списка
`stops` (проверено на реальном ответе):

```json
{
  "stop_id": "7-0-8000",
  "name": "Бульвар Рокоссовского",
  "route": 7,
  "direction": 0,
  "sequence": 1,
  "lat": 55.717,
  "lon": 37.61,
  "is_hub": false,
  "value": 95914.63,
  "share": 0.1746
}
```

Поле называется `name`, не `stop_name`. `stop_id` составной
(маршрут-направление-номер), годится как ключ списка. `is_hub` стоит
у пересадочных узлов — метро, МЦК, МЦД, вокзалы; на карте их логично
рисовать крупнее, а в списке выделять. Сумма `value` по всем остановкам
равна `total` маршрута — проверено, распределение ничего не теряет.

`GET /api/stops?route=` отдаёт те же поля без `value` и `share` — годится,
когда нужны просто точки на карте без прогноза.

**Обязательно вывести на экран поле `note`** — там написано, что разложение
оценочное, потому что привязки валидаций к остановкам в данных нет. В ответе
также стоит флаг `estimated: true`. Это не формальность: если показать
остановочные числа без оговорки, на защите спросят, откуда они, и ответ
будет хуже, чем честная плашка.

Для маршрутов без координат ответ придёт с пустым списком и пояснением.

### 7. Блок рекомендаций

Самое дешёвое, что закрывает бизнес-ценность. Считается на фронте из уже
полученных чисел, бекенд не нужен.

Взять `summary.peak` из ответа прогноза и написать текстом:

> Маршрут 17, 15 декабря, 18:00 — прогноз 2 340 посадок, на 28% выше
> среднего для этого часа. Рассмотрите дополнительный выпуск.

Два-три таких пункта по самым нагруженным маршрутам. Формулировки должны быть
операционными: дополнительный выпуск, перераспределение состава, уточнение
расписания.

### 8. Строка состояния

```
GET /api/meta     → что загружено: период прогноза, период истории, файлы
GET /api/health   → статус, число строк, статистика кеша
```

Показать в шапке: до какой даты есть данные, какой период прогнозируется,
когда загружено. Стоит копейки, а превращает страницу из скрипта в продукт.

### 9. Плашка «маршрут не работает»

Эндпойнта пока нет, но контракт ниже зафиксирован — можно писать сразу,
подложив заглушку.

В ответе прогноза появится массив `network_events` с активными изменениями
сети на запрошенный период:

```json
{
  "points": [...],
  "network_events": [
    {
      "id": 3,
      "route": 17,
      "type": "FULL_CLOSURE",
      "valid_from": "2025-11-10",
      "valid_to": "2025-11-20",
      "hour_from": null,
      "hour_to": null,
      "factor": null,
      "title": "Ремонт путей",
      "source_url": "https://..."
    }
  ]
}
```

Если массив не пустой — над графиком показать предупреждение:

```
⚠ Маршрут 17 временно не работает
  Ремонт путей · 10–20 ноября · источник
```

**Важно: коэффициент применять не надо.** Значения в `points` уже
пересчитаны бекендом — при полном закрытии там нули, при укорочении уже
умножено. Если фронт домножит ещё раз, эффект применится дважды.

`valid_to` может быть `null` — это авария с неизвестным концом, писать
«с 10 ноября, до отмены».

Типы: `FULL_CLOSURE` (нули), `SHORTENING` и `MANUAL_MULTIPLIER`
(множитель в поле `factor`). На графике закрытые часы стоит подкрасить
или заштриховать, чтобы ноль не выглядел ошибкой загрузки.

### 10. Админская форма изменения сети

Это отдельный экран или модальное окно. Нужна для демо: на защите событие
добавляется руками за десять секунд, и следующий запрос прогноза уже
показывает ноль по закрытому маршруту.

```
Добавить изменение сети

Маршрут          [ 17 ▼ ]
Тип              [ Полное закрытие ▼ ]
С                [ дата ]
До               [ дата ]  ← можно оставить пустым: «до отмены»
Часы             [ с ] [ до ]  ← необязательно, пусто = все сутки
Коэффициент      [ 0.80 ]  ← только для укорочения и множителя
Название         [ Ремонт путей ]
Источник         [ URL ]

[ Добавить ]
```

Эндпойнты:

```
GET    /api/network-events           список активных
POST   /api/network-events           создать
DELETE /api/network-events/{id}      снять (например, движение восстановили)
```

Тело POST — те же поля, что в JSON выше, без `id`. Поле «Источник» важнее,
чем кажется: именно ссылка делает событие проверяемым, на защите по ней
покажут, откуда информация.

Рядом со формой — список уже активных событий с кнопкой снятия.

Пока эндпойнта нет, форму можно собрать на локальном состоянии и включить
запросы одной строкой, когда бек будет готов.

Пишите под то, что в первой колонке. Вторая появится позже сегодня и
не должна вас блокировать.

| Работает сейчас | Появится сегодня |
|---|---|
| `GET /api/forecast` со всеми фильтрами и коэффициентами | `GET/POST/DELETE /api/network-events` (задачи 9 и 10) |

| `GET /api/export`, `/api/export/submission` | |
| `GET /api/factors`, `/api/scope` | |
| `GET /api/health`, `/api/meta` | |

Формат существующих полей не изменится — добавится только массив

Переделывать ничего не придётся, поэтому задачи 9 и 10 можно писать

### Состояния загрузки и ошибок

Отдельным пунктом, потому что на демо это видно сразу. Нужны три состояния
на каждом блоке: загрузка, пусто, ошибка.

Ошибки приходят объектом с полем `detail` и понятным текстом на русском —
его можно показывать пользователю как есть, ничего переводить не надо.

Пустой ответ (`points: []`) означает, что под фильтр ничего не попало —
это не ошибка, так и надо написать. А если пустой прогноз приходит на всех
фильтрах, значит в сервис не подложен файл с данными: скажите в чат
команды, это не ваша проблема.

### Если останется время

Ускоренное воспроизведение истории: `GET /api/forecast?source=history`
с двигающимся курсором по датам, карта пульсирует, график заполняется,
на переходе через 1 ноября линия переключается с факта на прогноз.
Данные уже есть, писать нечего кроме таймера. Обязательна подпись, что это
воспроизведение исторических данных с ускорением, а не живой поток.

`GET /api/forecast/compare` отдаёт прогноз рядом с фактом за сопоставимый
по длине прошлый период — годится для блока «прогноз против факта».

## Подключение, сборка и Docker

Всё продукт едет одним контейнером: бекенд отдаёт и API, и собранный фронт.
Это буквально попадает в требование ТЗ «сервис — один контейнер», и жюри
запускает всё одной командой. Второй контейнер с nginx не нужен — это
третий конфиг, который может сломаться на демонстрации.

### В разработке

Vite поднимает свой сервер и проксирует API на бекенд:

```js
// frontend/vite.config.js
export default {
  server: {
    proxy: { '/api': 'http://localhost:8000' }
  }
}
```

Ходить **относительными путями**, без адреса бекенда в переменных:

```js
// frontend/src/api.js
const BASE = '/api'

export async function getForecast(params) {
  const query = new URLSearchParams(params)
  const response = await fetch(`${BASE}/forecast?${query}`)
  if (!response.ok) {
    const error = await response.json().catch(() => ({}))
    throw new Error(error.detail || `Ошибка ${response.status}`)
  }
  return response.json()
}
```

В разработке относительный путь перехватит прокси, в собранном виде он
попадёт в тот же origin, где лежит статика. Один и тот же код работает
и там, и там.

Если всё-таки нужно постучаться с другой машины — CORS в бекенде открыт
полностью, можно ходить по полному адресу. Для сдачи так делать не надо:
жюри придётся запускать две вещи и следить за совпадением адресов.

### Сборка

```bash
cd frontend
npm run build          # получится frontend/dist/
cp -r dist/* ../service/static/
```

Каталог `service/static/` пустой — сервис отдаёт только API. Появились
файлы — начинает отдавать интерфейс на `/`, API остаётся на `/api`.

### Dockerfile

Многоступенчатая сборка: node собирает фронт, python его отдаёт. Текущий
`service/Dockerfile` — это вторая половина без ноды, надо дописать первую
ступень и строку `COPY --from=frontend`.

```dockerfile
FROM node:20-slim AS frontend
WORKDIR /build
COPY frontend/package*.json ./
RUN npm ci
COPY frontend/ ./
RUN npm run build

FROM python:3.12-slim
ENV DATA_DIR=/data STATIC_DIR=/app/static
WORKDIR /app
COPY service/backend/requirements.txt ./requirements.txt
RUN pip install --no-cache-dir -r requirements.txt
COPY service/backend/app ./app
COPY --from=frontend /build/dist ./static
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1"]
```

Один воркер — так и надо, не опечатка. Состояние сервиса живёт в памяти
процесса, при двух воркерах добавленное закрытие маршрута увидит только
один из них. Причина подробно расписана в комментарии к Dockerfile.

### Порядок работы

Сначала поднять бекенд и открыть `/api/docs` — там можно подёргать все
эндпойнты руками и увидеть форму ответов. Это быстрее, чем читать код.
Дальше фронт пишется под работающее API, без заглушек: прогноз отдаётся
из памяти, задержек в разработке не будет.

## Готово, когда

Открывается одной командой, на одном экране видны карта и график,
переключаются три горизонта, работают фильтры, двигается коэффициент
и график сразу меняется, скачивается XLSX, по клику на маршрут видна
разбивка по остановкам с оговоркой, есть блок рекомендаций и строка
состояния. Добавленное через админскую форму закрытие маршрута сразу
видно на графике плашкой, и значения по нему обнулились.

Последний шаг обязателен: собрать `npm run build`, положить `dist/`
в `service/static/`, поднять контейнер и проверить, что всё открывается
на чистой машине. В рубрике записано, что без запускаемого сервиса балл
существенно снижается.
