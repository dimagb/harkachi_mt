# Контракт между ML и Backend — ОТМЕНЁН

> **Этот документ больше не действует.** Оставлен как история разбора:
> в нём зафиксировано, почему подход «делить на уже применённый
> коэффициент» ненадёжен — вывод принят обеими командами.
>
> Действующий контракт и план: **`docs/stas-mvp-architecture.md`**.
> Там `model_prediction` не меняется, редактируемые множители по умолчанию
> равны 1.0, и сценарий каждый раз строится заново от базы, без делений.

**Версия 1.1 (архив)**

## Что изменилось относительно 1.0

Правки внесены поверх исходного контракта. Спорные места помечены,
чтобы ML-сторона могла возразить.

| # | Что | Почему |
|---|---|---|
| 1 | `by_route` и `by_hour` стали **относительными** множителями к `value`, композируются | В 1.0 приоритет «route важнее hour» терял часовую детализацию: для маршрута 17 в 8 утра брался 0.52 вместо 0.33 — промах в полтора раза в самый весомый час |
| 2 | Зафиксирована единая функция разрешения коэффициента, обе стороны обязаны использовать её | В 1.0 контекст лежал на уровне «дата × маршрут», а коэффициенты могли быть почасовыми: деление при отмене сценария давало неверный результат |
| 3 | Добавлен `history.csv` в релиз | Дашборду нужен факт рядом с прогнозом, иначе бэкенд лезет в `labels/` вопреки разделу «что Backend не делает» |
| 4 | Описано поведение при нескольких факторах одной группы | Было не определено |
| 5 | Описано поведение при неизвестном имени фактора | Было не определено |
| 6 | Добавлены `generated_at` и метрики по маршрутам в `metrics.json` | Отладка релизов и экран качества модели |
| 7 | Явно оговорён маршрут 5 | Он в сетке, но нулевой; интерфейс должен это объяснять |
| 8 | Границы коэффициентов сделаны жёсткими | «Примерно в диапазоне» не проверишь автоматически |

---

## 1. Общий принцип

ML и Backend разрабатываются независимо.

Backend **не знает**, какая модель используется, как она обучается и какие
признаки применяются.

Единственная точка интеграции:

```text
ML pipeline
   ↓
release/latest/
   ├── submission.csv
   ├── forecast_context.csv
   ├── correction_factors.json
   ├── history.csv
   └── metrics.json
   ↓
Backend
```

Backend читает только содержимое `release/latest/`.

Если ML-модель меняется, Backend менять не нужно, пока сохраняется формат
этих файлов.

---

## 2. `submission.csv`

Основной прогноз. Разделитель `;`, кодировка UTF-8.

```csv
route;date;hour;prediction
1;2025-11-01;0;12
1;2025-11-01;1;7
17;2025-11-01;8;527
```

| Поле | Тип |
|---|---|
| `route` | int |
| `date` | `YYYY-MM-DD` |
| `hour` | int, 0..23 |
| `prediction` | number ≥ 0 |

Полная сетка: 10 маршрутов × 61 день × 24 часа = **14 640 строк**.
Маршруты: `1, 5, 7, 11, 12, 17, 25, 26, 28, 50`.

**Маршрут 5.** В исходных данных по нему только нули — подтверждено
организаторами, это их ошибка выгрузки. ML всегда пишет по нему нули,
Backend помечает его признаком `excluded: true` и не показывает в
интерфейсе как обычный маршрут, чтобы не выглядело сбоем.

Backend использует `submission.csv` как **базовый прогноз**.

---

## 3. `forecast_context.csv`

Описывает контекст, уже учтённый в `submission.csv`.

Гранулярность: **дата × маршрут**.

```csv
date;route;day_type;is_holiday;event_active;event_type;season_mode;applied_factors
2025-11-04;17;holiday;1;0;;regular;calendar.holiday_on_weekday
2025-11-08;50;weekend;0;1;route_suspended;regular;event.route_50_weekend_suspended
```

`applied_factors` — список коэффициентов, уже заложенных в базовый прогноз.
Несколько значений разделяются запятой. Пустое поле означает, что
дополнительных факторов не применялось; при чтении CSV оно может стать
`null` или пустой строкой — Backend трактует оба варианта как «факторов нет».

**Важное ограничение гранулярности.** Контекст лежит на уровне дня, а
коэффициент может иметь часовую детализацию. Поэтому обе стороны обязаны
использовать **одну и ту же функцию разрешения** (раздел 6): ML применяет
фактор именно так, Backend именно так же его отменяет. Иначе деление даст
неверный результат.

---

## 4. `correction_factors.json`

Коэффициенты для сценариев «что если» в интерфейсе.

Группы: `calendar`, `school_holiday`, `weather`, `event`, `seasonality`.

```json
{
  "schema_version": "1.1",
  "model_version": "decomp_v2+events",
  "generated_at": "2025-09-26T14:20:00Z",
  "baseline": "обычный день без дополнительных факторов",
  "factors": {
    "calendar": {
      "holiday_on_weekday": {
        "value": 0.474,
        "by_route": { "1": 0.95, "17": 1.10 },
        "by_hour":  { "7": 0.61, "8": 0.70, "13": 1.31, "18": 1.03 },
        "n_obs": 8,
        "label": "Праздник, выпавший на будний день"
      }
    },
    "weather": {
      "rain_heavy": { "value": 0.927, "label": "Сильный дождь" }
    },
    "event": {
      "route_50_weekend_suspended": { "value": 0.056, "label": "Маршрут 50 закрыт по выходным" },
      "route_closed": { "value": 0.0, "label": "Полное закрытие маршрута" }
    },
    "seasonality": {
      "summer_mode": { "value": 0.823, "label": "Летний режим" }
    }
  }
}
```

Поле `label` необязательное, но желательное: интерфейс показывает его
пользователю вместо технического имени.

---

## 5. Что означает коэффициент

Коэффициент — мультипликатор относительно базового сценария.

`weather.rain_heavy = 0.927` означает, что прогноз при сильном дожде
примерно равен базовому, умноженному на 0.927.

---

## 6. Разрешение коэффициента (единственная верная формула)

**Это изменение относительно версии 1.0.** Раньше `by_route` и `by_hour`
были абсолютными альтернативами с приоритетом маршрута, из-за чего часовая
детализация терялась. Теперь они — **относительные поправки к `value`**.

```text
factor(route, hour) = value
                      × by_route.get(route, 1.0)
                      × by_hour.get(hour, 1.0)
```

Смысл: `value` — эффект в среднем, `by_route` — во сколько раз на этом
маршруте эффект сильнее или слабее среднего, `by_hour` — то же по часам.

Пример из JSON выше: праздник на маршруте 17 в 8 утра даёт
`0.474 × 1.10 × 0.70 = 0.365`. Утренний пик в праздник проседает сильнее,
чем день в целом, и это именно то, что нужно учесть.

**Требования к ML-стороне.** Значения `by_route` и `by_hour`
нормализованы так, что их средневзвешенное по объёму равно 1.0. Иначе
общий уровень поедет. Если нормализовать не получается, поле лучше не
отдавать вовсе — тогда берётся только `value`.

**Требование к обеим сторонам.** ML применяет фактор к базовому прогнозу
по этой же формуле. Только так деление при отмене сценария вернёт
исходное значение.

---

## 7. Сценарный пересчёт

Фактор **не был применён** в базовом прогнозе:

```text
prediction_scenario = prediction_base × factor(new)
```

Фактор **уже был применён** (указан в `applied_factors`):

```text
prediction_scenario = prediction_base × factor(new) / factor(applied)
```

Это защищает от двойного учёта. Значения `factor()` считаются по формуле
из раздела 6 для того же маршрута и часа.

---

## 8. Пример: праздник уже учтён

Контекст: `2025-11-04`, маршрут 17, `applied_factors = calendar.holiday_on_weekday`.

Пользователь оставляет сценарий как есть: `multiplier = factor / factor = 1`.
Прогноз не меняется.

## 9. Пример: праздник → обычный день

Базовый прогноз содержит праздничный коэффициент. Пользователь хочет
посмотреть обычный день, то есть `factor(new) = 1.0`:

```text
multiplier = 1.0 / factor(applied)
```

Для маршрута 17 в 8 утра это `1.0 / 0.365 = 2.74`.

## 10. Пример: добавить дождь

Погода в базовом прогнозе не учитывалась:

```text
prediction_scenario = prediction_base × 0.927
```

---

## 11. Несколько факторов

**Разные группы** применяются последовательно:

```text
prediction = base × weather_mult × event_mult × seasonality_mult
```

Для каждого фактора отдельно проверяется, был ли он уже применён.

**Одна группа.** В пределах одной группы одновременно активен **не более
одного** фактора. Это ограничение интерфейса: группы задуманы как
взаимоисключающие режимы (нельзя одновременно «лёгкий дождь» и «сильный
дождь»). Если в запросе пришло два фактора одной группы, Backend
возвращает `400` со списком конфликтующих имён.

**Неизвестное имя фактора.** Backend возвращает `400` и перечисляет
доступные имена в этой группе. Молча игнорировать нельзя — пользователь
решит, что сценарий применился.

---

## 12. Допустимый диапазон

```text
0 ≤ factor ≤ 3
```

Значения вне диапазона — ошибка загрузки релиза, а не предупреждение:
Backend отказывается принимать такой `correction_factors.json` и пишет
в лог, какой именно фактор не прошёл. Обрезать значения молча нельзя.

Это относится к итоговому `factor(route, hour)` после композиции, а не
только к `value`.

---

## 13. Коэффициент 0

`event.route_closed = 0` означает полное закрытие: сценарный прогноз равен
нулю.

Деление на ноль невозможно. Если в базовом прогнозе уже применён фактор
со значением 0, восстановить исходное значение через отношение нельзя —
информация потеряна безвозвратно.

**Правило:** ML **не применяет** нулевые факторы к базовому прогнозу.
Если маршрут закрыт, это отражается в самом прогнозе (там просто малые
значения), а нулевой фактор существует только как сценарий для интерфейса.
Если ML всё же применил нулевой фактор, он обязан указать это в
`applied_factors`, и Backend в этом случае блокирует отмену сценария и
показывает пользователю пояснение.

---

## 14. `history.csv`

**Новый файл.** Фактические посадки за исторический период — нужны
дашборду, чтобы показывать факт рядом с прогнозом и строить годовой
горизонт.

```csv
route;date;hour;boardings
17;2025-10-31;8;1842
```

Формат идентичен `submission.csv`, отличается только имя колонки значения.
Период: вся доступная история (январь–октябрь 2025).

Полная сетка не обязательна, но отсутствующие часы Backend трактует как
ноль — в исходных данных ночные часы просто не записаны.

Без этого файла Backend вынужден читать `labels/` напрямую, что
противоречит разделу 18.

## 15. `metrics.json`

```json
{
  "model_version": "v2r_events",
  "generated_at": "2025-09-26T14:20:00Z",
  "validation": {
    "wape_score": 0.8868,
    "protocol": "train янв-авг → predict сен-окт",
    "by_route": { "17": 0.901, "50": 0.612 }
  },
  "leaderboard_score": 0.86923,
  "use_events": true,
  "sources": ["calendar", "weather", "school_holidays", "events", "seasonality"]
}
```

`by_route` нужен экрану качества модели и защите перед жюри: видно, где
модель слабее и почему.

Backend не обязан использовать этот файл для основных эндпойнтов прогноза.
Он нужен для версии модели, отладки, `/api/model/info`, README и
демонстрации.

## 16. Папка релиза

```text
release/
├── latest/
│   ├── submission.csv
│   ├── forecast_context.csv
│   ├── correction_factors.json
│   ├── history.csv
│   └── metrics.json
├── v1r_no_events/
└── v2r_events/
```

Backend всегда читает `release/latest/`.

Рекомендация: `latest` — это копия, а не симлинк. Симлинки плохо
переживают монтирование томов в Docker на Windows.

## 17. Что Backend делает при старте

```text
1. читает submission.csv, проверяет структуру
2. загружает прогноз в память
3. читает forecast_context.csv
4. читает correction_factors.json, валидирует диапазоны
5. читает history.csv (если есть)
6. читает metrics.json
7. поднимает API
```

Если `submission.csv` не прошёл проверку — сервис не стартует и пишет
внятную ошибку. Если отсутствуют необязательные файлы (`history.csv`,
`metrics.json`) — стартует с предупреждением и отключает зависящие от них
возможности.

Перезагрузка релиза без перезапуска: `POST /api/reload`.

---

## 18. Минимальные проверки Backend

`submission.csv`:

```text
ровно 14 640 строк
нет дублей по route + date + hour
prediction >= 0 и не пустой
hour ∈ [0, 23]
route ∈ допустимом списке
даты покрывают 2025-11-01 … 2025-12-31 без пропусков
```

`forecast_context.csv`:

```text
есть date и route
нет дублей по date + route
даты входят в период прогноза
все имена в applied_factors существуют в correction_factors.json
```

Последняя проверка важна: опечатка в имени фактора приведёт к тому, что
Backend не сможет отменить сценарий и молча выдаст неверные числа.

`correction_factors.json`:

```text
валидный JSON
есть schema_version и factors
итоговый factor(route, hour) ∈ [0, 3] для всех комбинаций
by_route и by_hour нормализованы (средневзвешенное ≈ 1.0)
```

---

## 19. Что Backend НЕ делает

```text
не обучает ML
не строит признаки
не читает train.csv / test.csv
не пересчитывает коэффициенты из истории
не знает про CatBoost, LightGBM и прочее
не изменяет submission.csv
```

Backend только читает артефакты, отдаёт базовый прогноз, строит агрегации,
применяет сценарии и отдаёт данные фронтенду.

## 20. API-схема

```text
submission.csv                    → GET  /api/forecast            → базовый прогноз
+ forecast_context.csv
+ correction_factors.json         → POST /api/forecast/scenario   → сценарный прогноз
correction_factors.json           → GET  /api/factors             → каталог факторов для UI
metrics.json                      → GET  /api/model/info          → версия и метрики
history.csv                       → GET  /api/history             → факт для сравнения
```

`GET /api/factors` отдаёт фронтенду список доступных сценариев с
человекочитаемыми названиями — из него строится панель коэффициентов.

Тело `POST /api/forecast/scenario`:

```json
{
  "routes": [17, 25],
  "date_from": "2025-12-01",
  "date_to": "2025-12-31",
  "horizon": "month",
  "scenario": {
    "weather": "rain_heavy",
    "calendar": null,
    "event": "route_closed"
  }
}
```

`null` означает «убрать фактор этой группы», то есть привести к базовому
сценарию — именно здесь работает деление на уже применённый коэффициент.

Ответ содержит и скорректированные значения, и описание того, какие
множители применились к каждой точке. Это нужно интерфейсу, чтобы
показать пользователю, из чего сложился результат.

---

## 21. Главное правило интеграции

ML отвечает за содержание файлов. Backend — за их чтение, агрегацию и
применение сценариев. Ни одна сторона не зависит от внутренней реализации
другой.

Пока структура файлов сохраняется, ML и Backend разрабатываются и
обновляются независимо.

## 22. Тест на согласованность

Перед сдачей обе стороны прогоняют один и тот же тест: взять дату, где
`applied_factors` непустой, применить сценарий «как есть» и убедиться,
что прогноз не изменился ни на одну единицу.

```python
# для каждой строки forecast_context с непустым applied_factors
scenario_same = base × factor(applied) / factor(applied)
assert scenario_same == base
```

Если не сходится — значит, ML и Backend по-разному разрешают
коэффициент (раздел 6), и все сценарные числа неверны.
